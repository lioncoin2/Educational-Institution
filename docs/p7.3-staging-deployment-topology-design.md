# P7.3 — Staging deployment topology (design)

**Date:** 2026-10-03. **Status: DESIGN ONLY — nothing executed, committed or deployed.**
**Target: STAGING first**, checked as strictly as production (the env contract is shared).

This document answers the open infrastructure decisions that left P7.1.1 **BLOCKED**
([p7-livekit-deployment-verification.md](p7-livekit-deployment-verification.md) §8;
[p7-livekit-readiness.md](p7-livekit-readiness.md) §18) and the still-open parts of
[Q65](architecture/open-questions.md#q65--media-hosting-and-operations), under three owner
decisions received 2026-10-03:

- **D1 — TLS terminator is nginx.** It must carry HTTPS, WebSocket/WSS, and a TCP stream for
  TURN-over-TLS. No experimental Caddy L4 plugins.
- **D2 — TURN is required for production and must not be deferred.** The known Firefox TURN-relay
  failure on the committed bridge network must not be silently accepted; do not switch to host
  networking yet; first compare (A) the current bridge topology, (B) LiveKit host networking,
  (C) a separate TURN topology, then recommend one.
- **D3 — Postgres 16 and Redis are dedicated Docker containers on this VPS with persistent
  volumes.** Not Ubuntu host packages.

It changes **no code and no configuration**. It modifies no SSH, no firewall, creates no
production secret, runs no migration, starts no container, and is not committed or pushed. The
reader is the owner; §9 is the sequence to run **only after the §10 approvals**.

Grounding: owner decisions A–H ([open-questions.md Q65](architecture/open-questions.md#q65--media-hosting-and-operations));
the port map, TLS and TURN contracts ([readiness §7–§9](p7-livekit-readiness.md)); the Firefox
relay root cause and the bridge/host/`proxy_protocol` analysis

([communities-live-attendance.md §20.2](architecture/communities-live-attendance.md)); and the
API's own config rules (`backend/src/platform/config/livekit-config.ts`, `backend/.env.example`).

## 0. The D2 comparison — bridge vs host networking vs separate TURN

### 0.1 The problem, restated from source

TURN only matters for clients whose network blocks both UDP 7882 and TCP 7881 (some school and
home networks); ordinary SFU media never touches it (readiness §9). Every TURN allocation —
whether it arrives over TURN/UDP 3478 or TURN/TLS 5349 — binds **one UDP relay port** in
LiveKit's network namespace, and its **only peer is the SFU at `NODE_IP:7882`** (deployment-verification §5).

The failure is on the **relay ↔ SFU internal path**, so it afflicts TURN/UDP and TURN/TLS alike:

- LiveKit's embedded TURN and the SFU share one process. The SFU's socket is bound to the
  **container's** address; `NODE_IP` is **not** an address inside the container.
- So every relay→SFU datagram leaves the container for the host and must hairpin back through
  Docker's NAT. Across Docker 27.5→29.8, either firewall backend and either `userland-proxy`
  setting, the SFU is shown the **bridge gateway**, not `NODE_IP`.
  - Docker 27's default proxy: the relay then **drops the SFU's replies** → relayed ICE fails.
  - Otherwise the SFU pairs only through a **peer-reflexive gateway address**, which LiveKit
    treats as **unsupported for Firefox** (`pkg/rtc/clientinfo.go:57-59`): LiveKit disables
    "prflx over relay" for Firefox, so Firefox needs the relayed packets to arrive from exactly
    `NODE_IP:<port>`.
- **Publishing the relay range fixes nothing** (the source address is still rewritten) and would
  spawn ~20,000 `docker-proxy` processes (Compose expands the range per port).

Separately, on the **client-facing** TURN/TLS path, LiveKit echoes the TCP peer it sees as the
XOR-MAPPED-ADDRESS. **Firefox 157 rejects a loopback/link-local/wildcard** mapped address and
abandons the allocation; a private address passes (deployment-verification §6). This is why
`proxy_protocol` becomes necessary once the terminator connects from loopback.

### 0.2 The three architectures, evaluated

| Criterion | **A — current bridge** | **B — LiveKit host networking** | **C — separate TURN service** |
| --- | --- | --- | --- |
| **Firefox compatibility** | **Broken.** relay↔SFU hairpins to the gateway; Firefox relay fails (INFERRED from source + lab) | **Works.** relay↔SFU is `NODE_IP↔NODE_IP` by local delivery; lab carried media both ways (pion client, not a browser) | **Works in principle.** client's relay candidate is the standalone relay's own public address — a clean relay candidate, not prflx; not the LiveKit-embedded hairpin. **Not analysed in-repo** |
| **Docker isolation** | Full network-namespace isolation (best) | **Container kept, network namespace shared with host** (the decision-B trade-off, §7) | SFU keeps full bridge isolation; the TURN box is a new isolated unit |
| **LiveKit signalling (7880)** | `127.0.0.1:7880` published; API uses `livekit:7880` | 7880 bound to `127.0.0.1` (nginx) + the bridge gateway (API); no service-name alias | unchanged from A or B depending on how the SFU runs |
| **API → LiveKit control** | `http://livekit:7880` (service name) | **Changes:** `http://<private-host/gateway IP>:7880` (service name no longer resolves) | unchanged from the SFU's own mode |
| **Public media ports** | 7881/tcp, 7882/udp published 1:1 | 7881/tcp, 7882/udp on host interfaces | SFU: 7881/7882; relay box: its own UDP + TLS |
| **TURN/UDP (3478)** | published, but relay path unsound | on host; relay path sound | on the relay box; sound |
| **TURN/TLS (5349→443)** | relay path unsound even if TLS works | sound; needs `proxy_protocol` (see below) | on the relay box behind nginx |
| **`proxy_protocol`** | **off** (gateway is private → Firefox accepts) | **required** (terminator is `127.0.0.1` → Firefox rejects without it); default trusted CIDR `127.0.0.0/8` already matches | required if the relay sits behind the terminator; trusted CIDR set to the relay/nginx source |
| **Relay range** | overlaps Linux ephemeral by 7,233 ports; never public | pick a sub-range below 32768, or reserve via `ip_local_reserved_ports` | the relay box owns its range; no host overlap |
| **Security** | best isolation; open-relay peer issue (§7) still applies | shares host net ns; `proxy_protocol` trust surface; open-relay issue | largest surface (a new internet-facing daemon + its credentials) but SFU stays isolated |
| **Maintainability** | simplest files, but **does not work** | one `network_mode: host` + a few `livekit.yaml` keys; one new component behaviour to understand | a whole new service (coturn or a second LiveKit) to configure, secure, credential-bridge and patch |
| **Multi-node migration** | n/a (broken) | clean: when LiveKit moves to its own node (§20.2 steps 1–2) host networking is the norm there anyway | **this is the end-state** for scale (§20.2 step 3: "a dedicated server") |

### 0.3 Recommendation — **B (LiveKit host networking) with LiveKit's embedded TURN**

Grounded in the owner's own decision **F** ("Use LiveKit's **supported** TURN mechanism **unless a
separate TURN service is shown to be necessary**"):

1. **B makes the embedded TURN work** (lab-verified relay path), so a separate service is **not
   shown necessary** — decision F says stay with embedded.
2. **B is the minimal, verified delta** from the committed topology: `network_mode: host` plus a
   handful of `livekit.yaml` keys and the API→LiveKit address. No new daemon, no new credential
   system, no unanalysed component on the public internet.
3. **A is rejected** per D2 — it cannot carry Firefox relays and must not be silently accepted.
4. **C is the documented end-state**, not the near-term answer: it belongs at
   [§20.2 step 3](architecture/communities-live-attendance.md), when LiveKit moves to a dedicated
   media node and a standalone relay is the natural split. Adopting it now adds the largest
   attack surface and the most operations for a single staging VPS, for no capability B lacks.

**The one honest cost** is decision **B**'s wording: it asked for isolation "at the process and
container boundary." Host networking keeps the **container** (filesystem, PID, dropped
capabilities, `no-new-privileges`) but **shares the host network namespace**. The
deployment-verification doc flags this explicitly as "the owner's call." It is therefore the
first item in §10.

## 1. Final proposed topology

One VPS. Two trust zones.

```
                          Internet
                             │
        ┌────────────────────┼─────────────────────────────┐
        │ public: 443/tcp, 7881/tcp, 7882/udp, 3478/udp     │
        ▼                                                    ▼
  ┌───────────────────────────────────────┐      media (DTLS-SRTP, direct ICE
  │ nginx  (host, owns 443 + certs)        │      to NODE_IP:7882 / :7881) and
  │  • https  ─┐  SNI demux on :443        │      TURN/UDP to NODE_IP:3478 reach
  │  • wss     │  (ssl_preread)            │      LiveKit directly on the host.
  │  • TURN/TLS┘                           │
  └───┬─────────────┬───────────────┬──────┘
      │ 127.0.0.1   │ 127.0.0.1     │ 127.0.0.1:5349 (TLS terminated here,
      │ :3000       │ :7880         │ plaintext + PROXY v2 → LiveKit)
      ▼             ▼               ▼
  ┌────────┐   ┌─────────────────────────────────────────────┐
  │  api   │   │ livekit  (network_mode: host)                │
  │(bridge)│   │   SFU 7881/tcp 7882/udp  (public)            │
  └──┬──┬──┘   │   signalling 7880        (loopback+gateway)  │
     │  │      │   TURN/UDP 3478          (public)            │
     │  │      │   TURN/TLS 5349          (loopback, proxypro)│
     │  │      │   relay range 30000–32767 udp (never public)│
     │  │      └─────────────────────────────────────────────┘
     │  │  API → LiveKit control: http://<gateway-ip>:7880
     ▼  ▼
  ┌──────────────── private bridge network "institution_default" ────────┐
  │   db (postgres:16)         redis            (no published ports;      │
  │   volume pgdata            volume redisdata   reachable only here)    │
  └───────────────────────────────────────────────────────────────────────┘
```

- **Zone 1 — private bridge (`institution_default`):** `api`, `db`, `redis`. The API publishes
  only `127.0.0.1:3000`. Postgres and Redis publish **nothing** — reachable solely by service
  name on the bridge. This is the D3 change: Postgres/Redis move from "the host's" external hosts
  into dedicated containers on this network.
- **Zone 2 — host network:** `livekit` (`network_mode: host`, decision B trade-off) and `nginx`
  (the host's existing terminator, now specified as nginx per D1).
- **The bridge gateway** (a fixed IP via compose IPAM, e.g. `172.30.0.1`) is how the bridged API
  reaches the host-networked LiveKit's signalling port.

## 2. Network / port map

Derived from [readiness §7](p7-livekit-readiness.md) and adjusted for host networking (B) + the
Postgres/Redis containers (D3).

| Port | Proto | Carries | Exposure | Who reaches it |
| --- | --- | --- | --- | --- |
| 443 | TCP/TLS | nginx: HTTPS (API), WSS (API `/realtime` + LiveKit signalling), TURN/TLS (TURN hostname), demuxed by SNI | **public** | internet |
| 80 | TCP | nginx: ACME/redirect only (cert issuance) | public | internet / ACME |
| 3000 | TCP | API, plain HTTP (incl. `/realtime` upgrade) | **loopback** `127.0.0.1` | nginx |
| 7880 | TCP | LiveKit signalling (`/rtc`, Twirp room API, `/rtc/validate`, `GET /` health) | **loopback + bridge gateway** | nginx (loopback), API (gateway) |
| 7881 | TCP | ICE/TCP media fallback — *always listens on every interface whatever `bind_addresses` says* (MTU) | **public** | clients |
| 7882 | UDP | ICE/UDP muxed media (replaces 50000–60000) | **public** | clients |
| 3478 | UDP | embedded TURN/UDP, advertised `turn:<NODE_IP>:3478` | **public** | clients |
| 5349 | TCP | embedded TURN/TLS (`external_tls`), advertised `turns:<TURN_DOMAIN>:443` | **loopback** `127.0.0.1` | nginx (+ PROXY v2) |
| 30000–32767 | UDP | TURN relay allocations (one per allocation); only peer is the SFU | **never public** | internal (host-local) |
| 5432 | TCP | Postgres 16 | **bridge only, not published** | `api` |
| 6379 | TCP | Redis | **bridge only, not published** | `api` |

**Firewall (design — not applied; the owner opens these):** public = `443/tcp`, `80/tcp`,
`7881/tcp`, `7882/udp`, `3478/udp`. Everything else stays private. The relay range is never
public. Record the ruleset before and after. **This document changes no firewall.**

**Advertised to clients** (unchanged from source): `wss://<LIVEKIT_URL host>` for signalling;
`NODE_IP:7882`/`:7881` for media; `turn:<NODE_IP>:3478?transport=udp` and
`turns:<TURN_DOMAIN>:443?transport=tcp` for TURN (LiveKit always advertises 443 for TLS whatever
its own `tls_port`).

## 3. Docker networking design

**Two network modes on one host, on purpose.**

- **`institution_default`** — a user-defined bridge with a **fixed subnet/gateway** declared in
  compose IPAM (so the gateway IP is stable, not whatever Docker picks):

  ```yaml
  networks:
    institution_default:
      ipam:
        config:
          - subnet: 172.30.0.0/24
            gateway: 172.30.0.1
  ```

  `api`, `db`, `redis` attach here. Service-name DNS (`db`, `redis`) works between them.

- **`livekit`** uses `network_mode: host`. It therefore has **no** bridge alias — the API can no
  longer use `http://livekit:7880`.

**The two cross-zone connections:**

1. **API → LiveKit control.** `LIVEKIT_API_URL: http://172.30.0.1:7880` (the bridge gateway, a
   **private IPv4** — accepted by `livekit-config.ts` as an internal host, so plain HTTP is
   allowed; the admin JWT never crosses a public network). LiveKit binds 7880 to
   `[127.0.0.1, 172.30.0.1]` via `bind_addresses` so both nginx (loopback) and the API (gateway)
   reach it. *The gateway IP is deployment-fixed here; confirm it does not collide on the host —
   §10.*
2. **nginx → API / LiveKit / TURN.** nginx on the host reaches `127.0.0.1:3000` (API, published
   on loopback), `127.0.0.1:7880` (LiveKit signalling), and `127.0.0.1:5349` (TURN/TLS). All on
   host loopback, which is why nginx is specified as host-level (not a bridge container): a bridge
   container cannot reach host loopback, and loopback is what keeps `proxy_protocol`'s default
   trusted CIDR (`127.0.0.0/8`) valid and 7880/5349 off the public internet.

**Hardening carried over from the committed compose** (unchanged): every container
`security_opt: no-new-privileges:true`, `cap_drop: ALL`, no privileged mode, no Docker socket.
LiveKit's config stays a read-only `:ro` mount. Host networking does **not** require any added
capability.

**Compose file layout (design):**

| File | Services | Notes |
| --- | --- | --- |
| `compose.yaml` | `api`, `livekit` | existing; `livekit` gains `network_mode: host`, loses its `ports:` list (host networking publishes directly) |
| `compose.turn.yaml` | `livekit` TURN env | existing; `proxy_protocol` becomes **on** for B |
| **`compose.data.yaml`** *(new)* | `db`, `redis` | the D3 addition; `api` gains `depends_on` on both |

## 4. PostgreSQL / Redis storage design (D3)

Both run as dedicated containers on `institution_default`, **pinned by tag + digest**, publishing
no host port.

**Postgres 16**

```yaml
db:
  image: postgres:16.<minor>@sha256:<digest>   # pin the exact 16.x
  environment:
    POSTGRES_USER: institution
    POSTGRES_DB: institution
    POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?set it in the environment file}
  volumes:
    - pgdata:/var/lib/postgresql/data           # persistent
  healthcheck:
    test: ["CMD-SHELL", "pg_isready -U institution -d institution"]
    interval: 10s
    timeout: 5s
    retries: 5
  restart: unless-stopped
  security_opt: [ "no-new-privileges:true" ]
```

- `DATABASE_URL=postgresql://institution:${POSTGRES_PASSWORD}@db:5432/institution` (service name).
- `POSTGRES_PASSWORD` is a **new per-environment secret** added to the env file (§10).
- **The image never migrates** (repo rule): migrations run from a checkout
  (`cd backend && DATABASE_URL=… npm run db:migrate`) at deploy time — listed in §9, **not run
  now** (D3 forbids it this phase).
- The named volume persists across container re-creation; it is **not** a backup (§8).

**Redis**

```yaml
redis:
  image: redis:7.<minor>@sha256:<digest>
  command: ["redis-server", "--appendonly", "yes"]  # persistence per D3
  volumes:
    - redisdata:/data
  healthcheck:
    test: ["CMD", "redis-cli", "ping"]
    interval: 10s
    timeout: 3s
    retries: 5
  restart: unless-stopped
  security_opt: [ "no-new-privileges:true" ]
```

- `REDIS_URL=redis://redis:6379` (service name).
- The repo treats Redis as **ephemeral state only, never business truth** (`backend/.env.example`).
  D3 asks for a persistent volume, so `--appendonly yes` is included for a warm restart — but this
  is convenience, not a durability requirement (§8).
- **Decision point (§10):** whether to set `requirepass` on Redis. On a private bridge with no
  published port it is low-risk, but a host-networked LiveKit can route to the bridge subnet, so a
  password is the cheap belt-and-braces.

LiveKit still has **no Redis** (single-node routing; `REDIS_HOST` never passed) — this Redis is
the API's alone.

## 5. nginx routing design (D1)

nginx owns public **443** and must serve three hostnames plus terminate a raw TURN/TLS stream.
The §6 terminator table maps each hostname to its upstream. The single-443 collision (HTTPS vs
TURN/TLS on one IP) is resolved by **SNI demux in the `stream` module** — no Caddy L4 plugin
(D1). Requires nginx with the `stream` + `stream_ssl_preread` modules (stock on Ubuntu's
`nginx-full` / `libnginx-mod-stream`); `proxy_protocol v2` needs nginx **mainline ≥ 1.31.4** when
sending v2 (v1 works on stable).

**Layer 1 — `stream{}` SNI demux on :443 (no termination here):**

```nginx
stream {
  map $ssl_preread_server_name $upstream {
    turn.staging.example.com   127.0.0.1:8444;   # → TURN/TLS terminator (layer 2b)
    default                    127.0.0.1:8443;   # → HTTPS/WSS vhost     (layer 2a)
  }
  server {
    listen 443;
    ssl_preread on;                              # read SNI without terminating
    proxy_pass $upstream;
    proxy_protocol on;                           # carry the real client IP inward
  }
}
```

**Layer 2a — `http{}` TLS vhost (API + LiveKit signalling):**

```nginx
http {
  server {                                       # API hostname
    listen 127.0.0.1:8443 ssl http2 proxy_protocol;
    server_name api.staging.example.com;
    # ssl_certificate … (nginx owns the cert, existing issuer)
    set_real_ip_from 127.0.0.1;                  # trust the layer-1 PROXY header
    real_ip_header proxy_protocol;
    location / { proxy_pass http://127.0.0.1:3000; proxy_http_version 1.1;
                 proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection "upgrade"; }
    # /realtime is the same server, same upgrade headers (readiness §8)
  }
  server {                                       # LiveKit signalling hostname
    listen 127.0.0.1:8443 ssl http2 proxy_protocol;
    server_name livekit.staging.example.com;
    location / { proxy_pass http://127.0.0.1:7880; proxy_http_version 1.1;
                 proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection "upgrade"; }
  }
}
```

**Layer 2b — `stream{}` TLS terminator for TURN/TLS → plaintext + PROXY v2 to LiveKit:**

```nginx
stream {
  server {
    listen 127.0.0.1:8444 ssl proxy_protocol;    # terminate TURN's TLS here
    # ssl_certificate for turn.staging.example.com (nginx owns it)
    set_real_ip_from 127.0.0.1;
    proxy_pass 127.0.0.1:5349;                    # LiveKit's external_tls listener
    proxy_protocol on;                            # LiveKit reads the client IP (v2)
  }
}
```

Why this shape (from source, deployment-verification §6):

- TURN/TLS **cannot** go through an HTTP proxy: the first bytes are a STUN Allocate and pion
  closes on anything else. It must be an L4 TLS termination forwarding raw bytes — hence the
  `stream` block, not a `location`.
- LiveKit under `external_tls` holds **no certificate**; nginx owns all three certs. No second CA
  (decision E).
- Because the terminator reaches LiveKit from **`127.0.0.1`**, Firefox would see a loopback
  XOR-MAPPED-ADDRESS and reject it — so `proxy_protocol on` is mandatory here, and LiveKit's
  `turn.proxy_protocol_trusted_cidrs` default (`127.0.0.0/8`) already matches. (This is the B-only
  requirement; on the rejected bridge topology `proxy_protocol` stayed off.)

The chained `proxy_protocol` (layer 1 → layer 2 → LiveKit) preserves the **original client**
address end to end; `set_real_ip_from 127.0.0.1` tells each inner hop to trust the previous one.

Full nginx config is **implementation**, not written here. The host's current terminator
ownership and cert issuer are still unread (§10).

## 6. LiveKit / TURN topology

`livekit/livekit.yaml` and the TURN override, adjusted for B. Changes from the committed files
are marked **[new]**.

```yaml
port: 7880
# [new] bind signalling to loopback (nginx) + bridge gateway (API) only — not every host IP
bind_addresses: ["127.0.0.1", "172.30.0.1"]

rtc:
  tcp_port: 7881
  udp_port: 7882
  use_external_ip: false          # NODE_IP is authoritative; no boot-time STUN (≈47s hang risk)
  # [new] pin the advertised/bound IP to NODE_IP so multi-address hosts (Docker bridges add IPs)
  #       don't make UDP ICE bind the wrong address and fail whole on some starts
  ips:
    includes: ["${LIVEKIT_NODE_IP}"]

room:
  auto_create: false
  enable_remote_unmute: false

turn:                              # from compose.turn.yaml (LIVEKIT_TURN_*)
  enabled: true
  domain: ${LIVEKIT_TURN_DOMAIN}
  udp_port: 3478
  tls_port: 5349
  external_tls: true
  # [new] required for B: terminator connects from 127.0.0.1; default trusted CIDR 127.0.0.0/8 fits
  # (set via LIVEKIT_TURN_* env — proxy_protocol_trusted_cidrs stays the loopback default)

# [new] relay range below Linux's ephemeral range (32768–60999) to avoid the 7,233-port overlap
#  30000–32767 = 2,768 ports ≈ 590 concurrent relayed participants at 4 allocations each
#  (alternative: keep 30000–40000 and reserve it with net.ipv4.ip_local_reserved_ports)

logging: { level: info, json: true }
```

- **Compose:** `livekit` gets `network_mode: host` and **drops its `ports:` list** (host
  networking binds directly). `NODE_IP=${LIVEKIT_NODE_IP}` as today. `proxy_protocol` turned on
  via the TURN env (`compose.turn.yaml`).
- **Why host networking is the whole fix:** with LiveKit in the host net namespace and `NODE_IP`
  a host address, relay↔SFU is `NODE_IP:<port> ↔ NODE_IP:7882` by **local delivery** — the hairpin
  disappears and Firefox's `NODE_IP:<port>` requirement is met (lab-verified, pion client).
- **Open-relay hardening (§7, §10):** LiveKit's TURN permission handler admits **any public
  peer**, not only `NODE_IP`. Set `turn.deny_peer_cidrs` to cover public space (allowing only
  `NODE_IP`) if the owner wants to close it — an owner decision; nothing set by default.
- **Pin unchanged:** LiveKit `v1.13.7` by tag + digest
  `sha256:6fd3b7088874c4d119160dd688798dfec852bc014786d392caad15f6f63912a3`.

## 7. Security implications

1. **Host network namespace shared (B's cost).** LiveKit keeps its container (dropped caps,
   `no-new-privileges`, read-only config) but shares the host network. Consequences and
   mitigations:
   - It can reach **host loopback** services — notably `127.0.0.1:3000` (the API). The API
     requires JWT auth, so this is exposure, not a bypass.
   - It can route to the **bridge subnet** (`172.30.0.0/24`), i.e. `db:5432` and `redis:6379`.
     Postgres requires a password; Redis should get `requirepass` (§4, §10) to match.
   - It cannot gain privileges it doesn't have (caps still dropped).
2. **`proxy_protocol` trust surface.** With it on, any process that can open `127.0.0.1:5349`
   could forge PROXY headers and, by announcing another client's address and closing, **delete
   that client's TURN allocations**. Mitigation: 5349 is loopback-only and the trusted CIDR is
   the loopback default; host-local access is the control. A v2 header (not v1) avoids the
   single-read fragility.
3. **Open TURN relay.** Up to 12 allocations/participant, credentials valid 300 s, relayable to
   arbitrary public peers unless `turn.deny_peer_cidrs` restricts to `NODE_IP` (§6). Decision in §10.
4. **Secrets, per environment, never shared.** The four existing secrets (`JWT_SECRET`,
   `STORAGE_SIGNING_SECRET`, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET`) plus the **new
   `POSTGRES_PASSWORD`** (and optional Redis password). Compose still refuses to start on any
   empty required secret; the API still refuses to boot if the three secrets are not distinct or
   are placeholders. Generate each with
   `node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"`.
   **No production secret is created in this phase** (owner constraint).
5. **Data stores not publicly reachable.** Postgres/Redis publish no host port; only the bridge
   and (routably) a host-networked LiveKit can reach them. This is a net **improvement** over
   external DB hosts if those were reachable off-box.
6. **TLS ownership unchanged in principle.** nginx owns all three certs via the existing issuer;
   LiveKit holds none; no second CA (decision E). Production/staging refuse `ws://`.
7. **API admin JWT stays off the public network.** `LIVEKIT_API_URL` is a private gateway IP over
   plain HTTP inside the host — never public.

## 8. Backup implications

| Data | Where | Is it business truth? | Backup design |
| --- | --- | --- | --- |
| **Postgres** (`pgdata`) | named volume on the VPS | **Yes — system of record** | A named volume is **not a backup**. Design: scheduled `pg_dump` (or `pg_basebackup` + WAL archiving for PITR) to **off-VPS** encrypted storage; defined cadence + retention; a periodic **restore test**. This is new work the D3 move creates — before, "the host's Postgres" may have had its own backups. |
| **Uploaded files** (`api-storage`, `STORAGE_LOCAL_ROOT`) | named volume | **Yes — user content** | Must also be backed up off-VPS (encrypted). Easy to miss because it is "just a volume". |
| **Redis** (`redisdata`) | named volume | **No — ephemeral** (repo rule) | AOF persists for warm restart only. **No backup required**; it is rebuildable. Do not treat it as recoverable truth. |
| **Secrets** (`env/staging.env`) | git-ignored file on the VPS | — | Stored in the owner's secret manager, **never in a backup in clear**, never committed. |
| **LiveKit** | stateless | — | Nothing to back up; reproduced from pinned image + committed config. |

Backups must never capture secrets in plaintext (env files, logs) and must be encrypted at rest
off the VPS. Retention/cadence are an owner decision (§10).
