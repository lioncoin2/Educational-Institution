# Storage

> Do NOT store large binary files directly in PostgreSQL.

The database holds metadata and references. Bytes live behind a
`StorageProvider`.

---

## 1. The split

| | Postgres | Storage provider |
| --- | --- | --- |
| Holds | `FileAsset` rows: id, kind, content type, size, owner, storage key, timestamps | the bytes |
| Queried by | every module that references a file | nothing — accessed by key |
| Backed up as | part of the database | separately, and far more cheaply |

Why it matters beyond the stated rule: binaries in Postgres inflate every dump,
every restore, every replica, and every vacuum. A 40 GB database of which 38 GB
is voice messages makes routine operations slow for reasons unrelated to the
data anyone queries. The separation also means an object store's lifecycle
rules — tiering, expiry — apply without any application change.

---

## 2. The port

```ts
export interface StorageProvider {
  createUploadUrl(request: UploadRequest): Promise<PresignedUpload>;
  createDownloadUrl(storageKey: string, expiresInSeconds: number): Promise<string>;
  exists(storageKey: string): Promise<boolean>;
  delete(storageKey: string): Promise<void>;
}
```

The shape is deliberately **presigned-URL-first**, even though the current
implementation is a local filesystem.

That is the decision worth explaining. A `save(bytes)` interface would be
simpler today and wrong tomorrow: it forces every upload through the API
process, which turns a 2500-student voice-note cohort into 2500 large request
bodies proxied through the application. Presigned URLs let the client talk to
the object store directly, and the API only ever issues permission.

Writing the port this way now means the S3 adapter is a drop-in. Writing it the
easy way would mean changing every caller when the first real object store
arrives.

## 3. Adapters

**`LocalStorageProvider`** — implemented and tested. Filesystem-backed, for
development and single-node deployment. It implements the *same signed-URL
contract* an object store does: the caller receives a URL carrying an expiry and
an HMAC, and only a request presenting a valid signature may use it.

- `createHmac('sha256', secret).update(`${key}:${expiresAt}`)`
- Verification is `timingSafeEqual` after a length check, and rejects an expired
  timestamp before doing anything else.
- `absolutePathFor()` resolves the key inside the storage root and **throws if
  it escapes**. Keys are generated by us and cannot contain traversal, but this
  is the last line of defence and costs nothing.

**`S3CompatibleStorageProvider`** — not written. It is the same interface backed
by presigned PUT/GET. No caller changes.

## 4. Upload policy

Validation lives in the domain (`file-policy.ts`), so it is enforced wherever an
upload is requested rather than at one endpoint:

```ts
ALLOWED_CONTENT_TYPES: Record<FileKind, readonly string[]>
MAX_BYTES:             Record<FileKind, number>
validateUpload(kind, contentType, sizeBytes): Result<void>
```

Per-kind rather than global: a voice message and a certificate scan have
genuinely different size and type expectations, and a single global limit is
always either too permissive for one or too restrictive for the other.

### Storage keys are generated, never accepted

```ts
buildStorageKey(kind, ownerId, assetId, extension)
//  → 'voice/2026/03/usr_123/ast_456.m4a'
```

The client's filename **never** appears in the key. This closes path traversal,
key collision, and the class of bugs where a filename is later interpreted as a
path by some other tool. The original name is kept as metadata, sanitized, for
display only.

Sanitization (`sanitizeOriginalName`) strips control characters and path
separators and truncates — for display safety, not for storage safety, because
storage safety comes from not using it at all.

## 5. The deferred half, stated clearly

Implemented and tested: the policy, the port, the local adapter, URL signing and
verification, key construction, path-escape refusal.

**Not implemented: the endpoint that receives an upload.** There is currently no
route that accepts bytes. The `FileAsset` entity and its repository are also not
written.

This is noted in the adapter's own doc comment so a reader of the code finds it
without reading this file.

What that endpoint will need when it is written:

- Verify the signature and expiry before reading the body.
- Enforce the byte limit **while streaming**, not after buffering — otherwise
  the limit is decorative and the process is a memory-exhaustion target.
- Verify the actual content type against the declared one by inspecting the
  leading bytes. A declared `image/png` that is in fact something else is the
  oldest upload trick there is.
- Move from a quarantine key to the final key only after validation.

## 6. Access control

Every download goes through a signed URL with a short expiry. A URL is a
capability: possession grants access, so the expiry is the only thing limiting
how far it travels.

The authorization decision — *may this principal read this asset* — happens
**before** a download URL is minted, through the usual
`AuthorizationService`. `files` does not know what an asset means, so it cannot
make that decision itself; the module that owns the reference does.

Signed URLs are not currently bound to a principal. Binding them (adding the
`userId` into the signed payload) is a one-line change and is worth doing before
any asset can be genuinely sensitive; it is listed as technical debt rather than
done, because there is no upload endpoint yet for it to protect.

- `FileAsset` entity and repository.

- Image/audio transcoding.
