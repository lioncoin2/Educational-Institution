# Persistence

PostgreSQL is the system of record. Redis is for things that may be lost.

The instruction that bounded this:

> Do not create a huge schema just because future features might exist. Only
> establish the minimum foundation required for the architecture.

So there are **three tables**: `users`, `user_roles`, `audit_log`. Nothing
speculative.

---

## 1. Drizzle, and the reason it is not Prisma

Full reasoning in
[decisions/0008-drizzle-over-prisma.md](decisions/0008-drizzle-over-prisma.md).
The short form is a boundary argument, not a taste argument:

Prisma requires **one global `schema.prisma`**. Every module's tables in one
file, edited by everyone, with no mechanism preventing a query in `messaging`
from joining `operations`' tables. That single file would quietly undo the
module boundaries the rest of this architecture spends its effort enforcing.

Drizzle lets each module declare its tables beside the adapter that uses them:

```
src/modules/identity/infrastructure/schema.ts   ← identity owns these tables
src/platform/audit/schema.ts                    ← platform owns this one
```

and `drizzle.config.ts` collects them by glob:

```ts
schema: ['./src/platform/**/schema.ts', './src/modules/*/infrastructure/schema.ts']
```

Table ownership now matches module ownership, and a module can be extracted
with its schema intact.

### The deliberate cost

`platform/database` creates the Drizzle handle **without a registered schema**:

```ts
export type Database = NodePgDatabase<Record<string, never>>;
```

Platform must not know what tables exist — `platform-knows-no-modules` forbids
it. The consequence is that Drizzle's relational query API (`db.query.users...`)
is unavailable. The select/insert builder, which is what repositories actually
use, is unaffected.

That is a real trade: a convenience API given up to keep an architectural rule
true. It is recorded here so the next person does not "fix" it by importing
every module's schema into platform.

## 2. Migrations

```bash
npm run db:generate   # diff the schema files → drizzle/NNNN_*.sql
npm run db:migrate    # apply pending migrations
```

Four rules:

1. **Generated SQL is committed and reviewed.** `drizzle/0000_*.sql` is in the
   repository. A migration is code: it gets read before it runs.
2. **Nothing auto-migrates on boot.** Applying schema changes is a deliberate
   deployment step, not a side effect of a pod restarting. An app that migrates
   on startup will eventually have three replicas migrating at once.
3. **Migrations are forward-only.** No `down`. A mistaken migration is corrected
   by a new one, because a `down` path is written when it is not needed and is
   wrong by the time it is.
4. **Destructive changes are split across releases.** Add the new column, deploy
   code that writes both, backfill, deploy code that reads the new one, drop the
   old one in a later release. Each step is independently revertible; a single
   rename is not.

## 3. The schema, and why each decision was made

### `users`

| Column | Notes |
| --- | --- |
| `id` | text primary key. Ids are generated by `IdGenerator`, not the database |
| `email` | unique, **stored normalized** (trimmed, lower-cased) |
| `display_name` | |
| `status` | text + CHECK, default `invited` |
| `password_hash` | scrypt, `$scrypt$N$r$p$salt$hash` |
| `created_at`, `updated_at` | timestamptz |

**Ids are application-generated.** `IdGenerator` mints them, not a database
sequence. The entity is therefore complete and valid *before* it is persisted,
which is what lets a use case raise an event referencing an aggregate without a
round trip — and what keeps an insert from being the moment an object becomes
real.

**Email uniqueness is enforced on a normalized column**, not a functional index
on `lower(email)`. Both work; the difference is where the normalization rule
lives. With a functional index the rule exists in two places — the repository
and the index — and they drift. Here the repository normalizes on write *and*
on lookup, and a plain unique constraint is then a true case-insensitive
guarantee. Tested: saving `Teacher@Example.COM` and looking up
`  TEACHER@example.com  ` finds the same row, and a second account on the same
address is rejected.

**`status` is a CHECK, not a Postgres enum.** Adding a value to a pg enum is a
migration that locks the type; a CHECK constraint is a cheap re-validate. The
authoritative list is the TypeScript union either way. Tested: an out-of-set
status is rejected by the database, not merely by TypeScript.

### `user_roles`

A join table (`user_id`, `role`) with `granted_at` and `granted_by`, not an
array column on `users`.

Role changes are exactly the kind of thing an institution audits. A row can
carry who granted it and when; an array element cannot. The FK cascades on
delete, so removing a user cannot leave orphaned grants — also tested.

Indexed on `user_id`, because every authenticated request resolves a principal's
roles by user id. That is the one query guaranteed to run on every request, so
it is the one index that is unambiguously justified.

### `audit_log`

Owned by **platform**, not by a module: every module writes to it through the
`AuditLog` port, and none of them owns accountability.

Append-only by convention — there is no update or delete path in the code. Two
indexes, matching the two questions an audit log exists to answer: *what did
this person do* (`actor_user_id`, `occurred_at`) and *what happened to this
record* (`resource_type`, `resource_id`, `occurred_at`).

If this table is ever exposed beyond the application, its database role should
hold INSERT and SELECT and nothing else.

## 4. Repositories

Every repository implements a port the **domain** declares. There are two
implementations of `UserRepository`, and nothing above can tell them apart:

| | `InMemoryUserRepository` | `DrizzleUserRepository` |
| --- | --- | --- |
| Used by | unit tests, dev without Postgres | production |
| Selected in | `identity.module.ts` | `identity.module.ts` |

Selection is one factory, keyed on whether `DATABASE_URL` was actually supplied:

```ts
config.database.configured ? new DrizzleUserRepository(db) : new InMemoryUserRepository()
```

Falling back rather than failing keeps `npm run start:dev` working with no
Postgres running, and makes the absence a deliberate state rather than a
connection error on the first login attempt. It mirrors how `live` falls back to
`FakeRtcProvider` without LiveKit credentials — one pattern, applied
consistently.

`save()` upserts the user and **replaces** its roles inside a transaction.
Replacement rather than diffing, because `User.roles` is the complete intended
set: a partial write would leave a user holding a role the caller believed it
had removed. Tested.

## 5. What is tested, and how

`drizzle-user-repository.spec.ts` — **10 integration tests against a real
Postgres 16**, exercising: round-trip with roles, email normalization on write
and read, duplicate-email rejection, role replacement, upsert-not-duplicate,
CHECK-constraint rejection, FK cascade, the empty-roles case, and independence
between users.

They run the **committed migrations** to build the schema, rather than a
hand-built one — otherwise the tests would prove the repository works against a
schema nobody deploys.

The suite runs when `TEST_DATABASE_URL` is set and skips otherwise, with an
announced warning:

```
[skip] DrizzleUserRepository: set TEST_DATABASE_URL to run the Postgres integration tests.
```

The announcement matters. A test that quietly disappears is indistinguishable
from a test that passes, and this is the only coverage the SQL layer has.

CI runs them against a Postgres service container, so they are not
opt-in in practice.

## 6. Redis

Configured, not yet used. The boundary is fixed now because it is the one that
gets violated under deadline:

**Redis may hold:** cache entries, ephemeral realtime state (the live
speaker-request queue, presence, participant counts), rate-limit counters, job
queues, short-lived tokens.

**Redis must never hold permanent business truth.** If losing a Redis key loses
something an institution would consider a fact — an attendance record, a grade,
a moderation decision — it belonged in Postgres.

The test: *if Redis were flushed right now, what would be lost?* The answer must
be "performance and some in-flight convenience", never "what happened".

## 7. Connection management

One pool per process, `max: 10`, created in `platform/database`. Closed on
shutdown via `OnApplicationShutdown`, so a redeploy does not leave sockets open
against Postgres.

`DatabaseModule` is composed explicitly by `AppModule` rather than being pulled
in by `PlatformModule`, so a unit test never opens a pool by accident.

Pool size should be raised deliberately, with Postgres's own `max_connections`
in view. Replicas × pool size is the number that matters, and it is the usual
way a healthy application exhausts a database.

## 8. Deliberately deferred

- Postgres adapters for `live` (rooms, sessions, moderation) — in-memory today.
- The `FileAsset` table — there is no upload endpoint for it to serve yet.
- A Drizzle-backed `AuditLog`. The table exists; the adapter still writes to the
  structured log. This is the most load-bearing gap listed here.
- Read replicas, partitioning, the transactional outbox.
- Any schema for the eight contract-only modules. Their tables get written when
  their code does.
