# P7.4 — External real-client test procedure (iPhone)

**Date:** 2026-10-03. **Status: PROCEDURE — nothing executed here.** Prepares the real external-client
tests P7.3 could not run from the server (browser media, screen share, reconnect, and the
**Firefox-over-TURN-relay** matrix). Infrastructure, firewall, DNS and SSH are unchanged; P8 is not started.

This document is derived from the actual backend contract (NestJS; no global route prefix; the API is
nginx-fronted at `https://api-staging.adlink4.com`). Every route is guarded by default (fail-closed).

## 0. Facts that shape the test

- **Base URL:** `https://api-staging.adlink4.com` (no `/api` prefix). Bearer auth: `Authorization: Bearer <accessToken>`.
- **Roles:** `TEACHER` carries identity perms `live.join`, `live.speak`, `live.moderate`. `STUDENT` carries
  only `live.join`, `live.raise_hand` (a listener who may ask for the floor, never take it). Creating a
  community needs `communities.create` → **OWNER/ADMIN only** (not TEACHER).
- **Moderator of a community** = a member granted the community capability `community.live.moderate`
  (and `community.live.start` to start sessions). The teacher needs this grant **and** the `live.speak`
  identity perm (TEACHER has it) to publish audio / screen-share.
- **Join returns a LiveKit ticket:** `POST /live/sessions/:id/join` → `{ sessionId, token, url, expiresInSeconds,
  expiresAt, role, media:{microphone,screen,screenAudio} }`. `url` is the client-facing `wss://livekit-staging.adlink4.com`.
  **The join `token` is valid for ~120 s to *start* the connection** (`LIVE_JOIN_TOKEN_TTL_SECONDS`), not the
  connected duration — connect the device promptly, or re-run join.
- **Grant/revoke/present propagate LIVE.** The server calls LiveKit `updateParticipant` to change a
  connected participant's permissions (`livekit-rtc-provider.ts:226`). The student **stays connected**; its
  client receives `ParticipantPermissionsChanged`. No re-join is needed when the floor is granted or revoked.
- **The client cannot choose anything.** Room name is server-generated (`live-staging-<sessionId>`), identity is
  the authenticated user id, display name comes from AccountDirectory, publish rights come from server-side
  standing. No live route accepts a body.
- **Test-client limitation only (not a product rule):** the *disposable web test client* runs in **Safari on
  iOS**, and **Safari-the-browser** has no `getDisplayMedia`, so it cannot capture a screen. This is a
  limitation of **this throwaway browser tool on iOS**, **not** an architectural or product restriction. For
  the purposes of *these* tests only, drive the teacher's screen share (tests 10–11) from a **desktop
  browser** and keep the iPhone as the **student**. Test 12 (student rejected from screen-sharing) is proven
  by the backend `403` regardless of any client capability.
- **Product scope (for context — not exercised by this procedure):** the final **native Flutter application
  is expected to support screen sharing on every target platform** — **iOS via ReplayKit**, **Android via
  MediaProjection**, and **Desktop/Web via browser screen capture**. The backend LiveSession/token/permission
  model is already platform-agnostic and supports all of these unchanged; only the client capture mechanism
  differs per platform. The Safari-on-iOS web limitation above applies solely to the disposable test tool and
  must not be read back into the product or the Live domain.
- **No browser can call the API directly** (CORS is disabled, `CORS_ORIGINS=` empty). The operator runs the
  curl control-plane on a laptop/server shell and pastes the resulting join `token` into the iPhone's media
  client. WebSocket media to LiveKit is not subject to CORS.
- **Media client:** the Flutter app has no LiveKit media client, so use the disposable browser client
  published alongside this procedure — **P7.4 LiveKit Test Client:**
  `https://claude.ai/artifact/NFEWia2paKd6bN1yaMc581` (private to the owner's claude.ai account; open it on
  the iPhone while signed in). It supports **Force TURN relay** (`iceTransportPolicy: 'relay'`) — the
  decisive lever for tests 16–17 — and an event log for permission changes, reconnects, and subscribed tracks.

## 1. One-time setup (operator shell with curl + jq)

```bash
API=https://api-staging.adlink4.com
j() { jq -r "$1"; }              # tiny helper

# 1a. Bootstrap the owner ON THE SERVER (one-time; password on stdin, never an arg):
#     ssh to the host, then:
#       printf '%s' 'OwnerPassw0rd!' | docker exec -i institution-api-1 node dist/cli/bootstrap-owner.js \
#         --email owner@adlink4.com --name "Staging Owner"
#     (or run from a checkout with DATABASE_URL set). Prints "Owner account created: <id>".

# 1b. Log in as owner -> OWNER_TOKEN
OWNER_TOKEN=$(curl -s -X POST $API/auth/login -H 'content-type: application/json' \
  -d '{"identifier":"owner@adlink4.com","password":"OwnerPassw0rd!"}' | j '.accessToken')

# 1c. Create the teacher and the student (owner token; needs users.manage)
TEACHER_ID=$(curl -s -X POST $API/admin/users -H "authorization: Bearer $OWNER_TOKEN" \
  -H 'content-type: application/json' \
  -d '{"displayName":"Teacher One","identifier":"teacher@adlink4.com","initialPassword":"TeachPassw0rd!"}' | j '.id')
STUDENT_ID=$(curl -s -X POST $API/admin/users -H "authorization: Bearer $OWNER_TOKEN" \
  -H 'content-type: application/json' \
  -d '{"displayName":"Student One","identifier":"student@adlink4.com","initialPassword":"StudPassw0rd!"}' | j '.id')
# An outsider for test 13 (created but never added to the community)
OUTSIDER_ID=$(curl -s -X POST $API/admin/users -H "authorization: Bearer $OWNER_TOKEN" \
  -H 'content-type: application/json' \
  -d '{"displayName":"Outsider","identifier":"outsider@adlink4.com","initialPassword":"OutPassw0rd!"}' | j '.id')

# 1d. Assign roles
curl -s -X POST $API/admin/users/$TEACHER_ID/roles -H "authorization: Bearer $OWNER_TOKEN" \
  -H 'content-type: application/json' -d '{"role":"TEACHER"}' >/dev/null
curl -s -X POST $API/admin/users/$STUDENT_ID/roles -H "authorization: Bearer $OWNER_TOKEN" \
  -H 'content-type: application/json' -d '{"role":"STUDENT"}' >/dev/null
curl -s -X POST $API/admin/users/$OUTSIDER_ID/roles -H "authorization: Bearer $OWNER_TOKEN" \
  -H 'content-type: application/json' -d '{"role":"STUDENT"}' >/dev/null

# 1e. Create the community (owner), add teacher+student as members
COMMUNITY_ID=$(curl -s -X POST $API/communities -H "authorization: Bearer $OWNER_TOKEN" \
  -H 'content-type: application/json' -d '{"title":"P7.4 Test Halaqa"}' | j '.id')
curl -s -X POST $API/communities/$COMMUNITY_ID/members -H "authorization: Bearer $OWNER_TOKEN" \
  -H 'content-type: application/json' -d "{\"userIds\":[\"$TEACHER_ID\",\"$STUDENT_ID\"]}" >/dev/null

# 1f. Make the teacher a live moderator who may start sessions
curl -s -X POST $API/communities/$COMMUNITY_ID/grants -H "authorization: Bearer $OWNER_TOKEN" \
  -H 'content-type: application/json' \
  -d "{\"userId\":\"$TEACHER_ID\",\"capabilities\":[\"community.live.moderate\",\"community.live.start\"]}" >/dev/null

echo "COMMUNITY_ID=$COMMUNITY_ID TEACHER_ID=$TEACHER_ID STUDENT_ID=$STUDENT_ID OUTSIDER_ID=$OUTSIDER_ID"
```

## 2. Per-run: log in, start a session, get join tickets

```bash
TEACHER_TOKEN=$(curl -s -X POST $API/auth/login -H 'content-type: application/json' \
  -d '{"identifier":"teacher@adlink4.com","password":"TeachPassw0rd!"}' | j '.accessToken')
STUDENT_TOKEN=$(curl -s -X POST $API/auth/login -H 'content-type: application/json' \
  -d '{"identifier":"student@adlink4.com","password":"StudPassw0rd!"}' | j '.accessToken')
OUTSIDER_TOKEN=$(curl -s -X POST $API/auth/login -H 'content-type: application/json' \
  -d '{"identifier":"outsider@adlink4.com","password":"OutPassw0rd!"}' | j '.accessToken')

# Teacher starts the session (needs live.moderate + community.live.start) -> SESSION_ID
SESSION_ID=$(curl -s -X POST $API/live/communities/$COMMUNITY_ID/sessions \
  -H "authorization: Bearer $TEACHER_TOKEN" | j '.id')
echo "SESSION_ID=$SESSION_ID"

# Join tickets (token valid ~120s to CONNECT — fetch just before pasting into a client)
join() { curl -s -X POST $API/live/sessions/$SESSION_ID/join -H "authorization: Bearer $1"; }
# join "$TEACHER_TOKEN"   -> paste .token/.url into the desktop client (teacher)
# join "$STUDENT_TOKEN"   -> paste .token/.url into the iPhone client (student)
```

## 3. The 17 tests

Legend — **Expected** is the API result; **LiveKit** is the media-plane behavior; **PASS** is the condition.
Error body shape: `{ "error": { "kind", "code", "message" }, "requestId" }`.

| # | Test | Endpoint · method · role | Expected API | LiveKit behavior | PASS / FAIL |
|---|------|--------------------------|--------------|------------------|-------------|
| 1 | Teacher joins Live | `POST /live/sessions/:id/join` · teacher | `200` `{token,url,role:"moderator",media:{microphone:true,screen:true,...}}` | Client connects to `wss://livekit-staging…`; teacher participant present, `canPublish:true` | PASS if connected and `role=="moderator"`, `media.microphone==true` |
| 2 | Student joins Live | `POST /live/sessions/:id/join` · student | `200` `role:"listener"`, `media:{microphone:false,screen:false}` | Student connects; `canPublish:false` | PASS if connected and `role=="listener"`, `media.microphone==false` |
| 3 | Student receives teacher audio | — (media plane) | n/a | After teacher enables mic, student's client fires `TrackSubscribed(audio)` and audio is audible | PASS if student hears teacher |
| 4 | Student mic starts disabled | from test 2 ticket | `media.microphone==false` | Student "Enable Mic" is rejected by LiveKit (no publish permission) | PASS if student cannot publish mic before a grant |
| 5 | Student raises hand | `POST /live/sessions/:id/hand` · student (`live.raise_hand`) | `201` `{request:{id,state:"pending",...}}` (`200` if already up) | none yet | PASS if `201` and a pending request exists |
| 6 | Teacher grants speaking | `GET /live/sessions/:id/hands` then `POST /live/requests/:requestId/grant` · teacher (`live.moderate`) | hands `200 {items:[{id,userId,displayName,state:"pending"}]}`; grant `200 {request:{state:"granted"},media}` | Server `updateParticipant` raises student's permission; student client fires `ParticipantPermissionsChanged` (canPublishAudio→true) | PASS if grant `200` and student permission flips live (no re-join) |
| 7 | Student publishes microphone | — (media plane, after 6) | n/a | Student "Enable Mic" now succeeds; teacher fires `TrackSubscribed(audio)` from student and hears it | PASS if teacher hears student |
| 8 | Teacher revokes speaking | `POST /live/requests/:requestId/revoke` · teacher (`live.moderate`) | `200 {request:{state:…},media}` | Server resets student permission (canPublish→false) and mutes/stops the mic track; student stays connected | PASS if student can no longer publish and remains in the room |
| 9 | Student becomes listener again | from 8 | `role` listener on next session view | Student `canPublish:false`; subscribes only | PASS if student is a listener with no publish |
| 10 | Teacher starts screen sharing | `POST /live/sessions/:id/screen-share` · teacher (`live.moderate` + `live.speak`) | `201` (slot taken) / `200` (already) | Teacher publishes a screen-share track **(drive from a desktop browser for this test — the Safari/iOS web test client can't capture a screen; the native app will, via ReplayKit/MediaProjection)** | PASS if `201` and a screen track is published |
| 11 | Student receives screen share | — (media plane) | n/a | Student client fires `TrackSubscribed(video, source=screen_share)` and renders it | PASS if student sees the shared screen |
| 12 | Student attempts screen share → rejected | `POST /live/sessions/:id/screen-share` · student | `403` `{code:"identity.permission_denied"}` (student lacks `live.moderate`) | No track; server never issues screen permission | PASS if `403 identity.permission_denied` |
| 13 | Unauthorized user attempts to join → rejected | `POST /live/sessions/:id/join` · outsider (not a member) | `404` `{code:"live.session_not_found"}` (no enumeration) | No token issued | PASS if `404 live.session_not_found` and no token returned |
| 14 | Teacher ends LiveSession | `POST /live/sessions/:id/end` · teacher (`live.moderate`) | `200` `{state:…,endedAt,endReason}` | LiveKit room ended; all participants disconnected (`Disconnected`) | PASS if `200` and clients disconnect |
| 15 | Client reconnects after network blip | — (media plane) | n/a | Toggle iPhone airplane mode ~10 s while connected: client fires `Reconnecting` then `Reconnected`; media resumes (session not ended) | PASS if the client auto-reconnects and media resumes |
| 16 | TURN connectivity | media plane, **Force TURN relay = ON** | n/a | With `iceTransportPolicy:'relay'`, the client connects and media flows **only** via TURN (3478/udp or 5349/tcp-over-443) | PASS if connect + audio works with relay forced |
| 17 | TURN relay from a restrictive external network | media plane, restrictive net | n/a | From a network that blocks UDP 7882 & TCP 7881 (e.g. strict cellular/guest Wi-Fi), **and in Firefox on a laptop on that network**, media still flows via TURN relay | PASS if media works on the restrictive network AND in Firefox (closes the D2 question); **investigate**, do not pass, if Firefox relay fails |

**Note on 16/17:** P7.3 verified TURN/UDP (STUN) and TURN/TLS termination from the server only. TURN *relay
of real media* — especially **Firefox** — is **NOT** considered verified until these two client tests pass
from a genuinely restrictive external network. Do not mark TURN relay verified from server-side evidence.

## 4. What to do on your iPhone — step by step

You are the **student**. Have a helper (or a second browser tab on a **laptop**) act as the **teacher**;
for tests 10–11 run the teacher from a **desktop** browser, because the disposable web test client on
**Safari/iOS** cannot capture a screen (a Safari-web limitation of the test tool only — the native Flutter
app will screen-share on iOS via ReplayKit, on Android via MediaProjection, and on Desktop/Web via browser
capture).

1. **Operator (laptop/server shell):** run Part 1 once, then Part 2 to get `SESSION_ID`. Keep the shell open.
2. **Teacher (desktop browser — Chrome or Firefox):** open the **P7.4 LiveKit Test Client** page. Operator runs
   `join "$TEACHER_TOKEN"`; paste the printed `url` and `token` into the page; tap **Connect** within ~120 s.
   Tap **Enable Mic** and allow the microphone.
3. **iPhone (Safari):** open the same **P7.4 LiveKit Test Client** page (the artifact URL). Operator runs
   `join "$STUDENT_TOKEN"`; paste the `url` and `token`; tap **Connect** within ~120 s.
   - **Test 1/2:** both show *Connected*; the iPhone shows role **listener**, mic controls **disabled**.
   - **Test 3:** you hear the teacher (allow audio autoplay if Safari prompts — tap the page once).
   - **Test 4:** tap **Enable Mic** on the iPhone — it is **refused** ("publish not permitted"). Expected.
4. **Raise hand (test 5):** operator runs the raise-hand curl as the student (or add a button in the client).
   On the teacher page you should see a pending hand.
5. **Grant (test 6/7):** operator runs the hands + grant curl as the teacher. On the iPhone, the mic control
   **enables by itself** (permission changed live). Tap **Enable Mic**, allow the microphone — the teacher now
   hears you.
6. **Revoke (test 8/9):** operator runs the revoke curl. On the iPhone the mic control **disables** again and
   your mic stops; you remain connected as a listener.
7. **Screen share (test 10/11):** on the **teacher desktop**, tap **Share Screen** and pick a window. The
   iPhone renders the shared screen. (Don't try Share Screen in the iPhone *web test client* — Safari/iOS
   can't capture a screen. This is a limit of the test tool only; the native Flutter app will screen-share on
   iOS via ReplayKit.)
8. **Student screen-share rejected (test 12):** operator runs the student screen-share curl → expect
   `403 identity.permission_denied`. (Nothing happens on the iPhone — correct.)
9. **Outsider rejected (test 13):** operator runs the join curl as the outsider → expect `404 live.session_not_found`.
10. **Reconnect (test 15):** while connected on the iPhone, turn **Airplane Mode on for ~10 seconds, then off**.
    The client shows *Reconnecting…* then *Reconnected*; audio resumes. (Do this before ending the session.)
11. **TURN forced (test 16):** **Disconnect** on the iPhone, tick **Force TURN relay**, fetch a fresh student
    token (`join "$STUDENT_TOKEN"`), paste, **Connect**. You should still connect and hear the teacher — now
    exclusively over TURN.
12. **TURN from a restrictive network (test 17):** repeat step 11 with the iPhone on **cellular data or a strict
    guest Wi-Fi** that blocks plain UDP. Then repeat on a **laptop running Firefox** on that same network. Media
    must still flow. If Firefox-over-relay fails, record it and investigate — do **not** mark TURN verified.
13. **End (test 14):** operator runs the end curl as the teacher → both clients disconnect. Done.

## 5. Reminders

- Do not open 30000–32767/udp, change DNS/SSH/firewall, or start P8 for these tests.
- If any join/start returns `503 live.media_unavailable` / `live.media_misconfigured`, the media provider or
  LiveKit is not ready — check `LIVE_MEDIA_PROVIDER=livekit` and LiveKit health before retrying.
- Join tokens expire ~120 s after issue; always fetch the token immediately before connecting a device.
