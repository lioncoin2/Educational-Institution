# P8.1 — Load-generation harness

**Date:** 2026-10-04. **Status: IMPLEMENTED — dry-run only, zero load generated.** This documents the load
harness built for P8 (plan: `docs/p8-load-capacity-plan.md`). It is a test/ops tool, isolated from the
production application, that *can* drive LiveKit media load, API/realtime load, and a read-only metrics
collector — but by default does nothing but validate and print a plan. No staging/runtime configuration was
changed to build it.

## Where it lives, and why

| Path | Contents | Why here |
|------|----------|----------|
| `backend/test/load/` | the harness: `core/`, `scenarios/`, `metrics/`, `livekit/`, `api/`, `cli/`, `tests/` | under `backend/` so it reuses the already-installed deps (`@livekit/rtc-node`, `livekit-server-sdk`, `ws`); under `test/` so `tsconfig.build` excludes it from the production image, and `npm test` runs its unit specs |
| `backend/test/livekit/load/media-driver.ts` | the **only** new file that imports `@livekit/rtc-node` | the architecture test (`test/architecture/livekit-suite.spec.ts`) asserts the WebRTC client is named only under `test/livekit/`. The rest of the harness reaches the driver by **dynamic import**, so no `test/load/` file names it. |

Nothing in `src/` was touched. The media driver is loaded lazily, so the default dry-run path imports no
WebRTC client and no network code.

## Architecture

```
cli/run.ts ──► core/config.ts  (parse argv, validate shape)      [pure]
           ──► core/safety.ts  (hard caps + gate: dry-run default) [pure]
           ──► scenarios/catalog.ts (13 deterministic scenarios)   [pure]
           ──► core/identity.ts (deterministic ids, loadtest- rooms)[pure]
   on real load only (gate = real-load):
           ──► metrics/collector.ts  (read-only /proc, docker, ss → CSV)
           ──► livekit/tokens.ts     (livekit-server-sdk AccessToken + RoomService)
           ──► livekit/media-run.ts ─dynamic import─► test/livekit/load/media-driver.ts (@livekit/rtc-node)
           ──► api/api-load.ts       (fetch + ws against the real API contracts)
```

- **core/** — configuration, validation, safety, deterministic identities. Pure, no I/O.
- **scenarios/** — the catalog of 13 P8 scenarios as data.
- **metrics/** — pure parsers (`parsers.ts`) + a run-scoped sampler (`collector.ts`) that only ever READS
  (`/proc/net/dev`, `/proc/net/snmp`, `/proc/net/softnet_stat`, `/proc/loadavg`, `/proc/meminfo`,
  `nf_conntrack_count`, `docker stats`, `ss -s`) and appends CSV.
- **livekit/** — SFU-direct token minting + room management (`loadtest-` prefix) and media orchestration.
- **api/** — real login + realtime WS handshake + paced HTTP loop.
- **cli/** — the entry point; dry-run by default.

## Build

Nothing to build — it runs from source with the repo's existing toolchain:

```bash
cd backend
npm ci                       # if deps are not already installed (installs @livekit/rtc-node etc.)
npx ts-node test/load/cli/run.ts --help
```

Unit tests run with the normal suite (`npm test`) or in isolation:

```bash
npx jest test/load
```

## Dry-run (default — generates no load)

```bash
cd backend
npx ts-node test/load/cli/run.ts --list
npx ts-node test/load/cli/run.ts --scenario lk-listeners-3000
```

A dry-run validates the scenario, prints the plan (rooms, participants, publishers, expected traffic, the
target it *would* hit, and the stop conditions), and exits without opening a socket. Exit codes: `0` dry-run
ok, `2` malformed scenario, `3` real run refused by the gate.

## Enabling real execution (later — NOT done in P8.1)

A real run requires **all** of: `--allow-load`, a `--target`, and a scenario within the hard caps. There is
no `--force`. Credentials come from the environment only (never committed):

```bash
# media (SFU-direct) — exports kept OUT of source control:
export LOADTEST_LIVEKIT_URL=wss://livekit-staging.adlink4.com
export LOADTEST_LIVEKIT_API_KEY=...        # the LiveKit API key
export LOADTEST_LIVEKIT_API_SECRET=...      # the LiveKit API secret
# api:
export LOADTEST_API_BASE=https://api-staging.adlink4.com
export LOADTEST_API_IDENTIFIER=...          # a disposable test account
export LOADTEST_API_PASSWORD=...

# then, from an OFF-BOX generator host (see below):
npx ts-node test/load/cli/run.ts --scenario lk-listeners-500 \
    --target wss://livekit-staging.adlink4.com --allow-load --out run.csv
```

The CLI prints a prominent `⚠ REAL LOAD WILL BE GENERATED` banner naming the target before it runs, and
refuses (exit `4`) if the needed `LOADTEST_*` env is absent.

## Scenario catalog

Thirteen deterministic scenarios (ids from `--list`): `api-baseline`, `lk-listeners-{10,100,500,1000,2000,
3000}`, `lk-multiroom-audio` (20×500 = 10k listeners), `lk-speakers-4`, `lk-screenshare`, `lk-relay-500`,
`lk-churn`, `combined`. Each carries its target plane, room/participant/publisher counts, relay flag, ramp,
hold, expected traffic, the §9 stop conditions, and the metric groups to capture. Any field is overridable per
run (`--rooms --listeners --speakers --screen --ramp --duration --relay --api-connections --api-rps`), and a
bare `--kind <plane>` builds a tiny custom scenario.

## Safety model

`core/safety.ts` enforces hard caps independent of scenario/flags — an accidental `--listeners 500000` cannot
become real load:

| Cap | Value | Rationale |
|-----|-------|-----------|
| total participants | 12,000 | above the 10k target, refuses runaways |
| participants/room | 3,500 | above the 3k/room target |
| rooms | 200 | matches plan multi-room ceiling |
| publishers/room · total | 50 · 2,000 | publishers cost far more than listeners; keep bounded |
| duration | 1,800 s | no single run over 30 min |
| ramp | 200/s | a slower admit avoids a self-inflicted connect storm |
| api connections · rps | 12,000 · 5,000 | matches the app's 10k realtime cap with headroom |

The gate (`decideGate`) returns **dry-run** unless `--allow-load` *and* `--target` are present *and* zero caps
are exceeded; `--allow-load` with a violation is a hard **refusal** (shown, not silently downgraded).

## Metrics

The collector samples the read-only counters above on `--interval` (default 2 s) and writes one CSV row per
sample, deriving per-second rates (tx Mbps, tx pps, rx Mbps) from consecutive counters, plus UDP/softnet drop
counters, load, MemAvailable, conntrack, established-conn count, and per-container (livekit/api) CPU/mem.
LiveKit has no Prometheus endpoint (plan F6), so media-plane detail (loss, bitrate, per-room) still comes from
the RoomService API + log rtpStats at run time; enabling `prometheus_port` remains an optional, approval-gated
config change.

## Off-box generation requirements

The P8 plan requires the generator to run **off-box** (running it on the staging VPS would contend for the
same cores/NIC and only exercise loopback). To stand up a generator host later (not provisioned here):

- A separate machine (or a few) with good upstream bandwidth and ≥ a few cores — `@livekit/rtc-node` uses
  native CPU per participant, so one host drives hundreds–low-thousands of listeners; the 10k target needs
  several hosts coordinated.
- Node 22 + this repo checked out + `npm ci` (installs `@livekit/rtc-node` native bindings).
- Network reach to the staging public endpoints: `443/tcp` (WSS signalling + TURN/TLS), `7882/udp` and
  `7881/tcp` (ICE), `3478/udp` (TURN) — the existing firewall already allows these from anywhere.
- The `LOADTEST_*` environment exported on the generator host only; secrets never committed.
- For the TURN-relay scenario, the generator may sit behind a UDP-restrictive network, or just use the
  harness's forced-relay flag (`relay: true`).

## Open questions / prerequisites surfaced

- **Q-P8-1 — RESOLVED.** `@livekit/rtc-node` supports forced relay: `RoomOptions.rtcConfig.iceTransportType =
  IceTransportType.TRANSPORT_RELAY`. The driver implements it; the `lk-relay-500` scenario uses it.
- **Q-P8-2 — OPEN.** The synthetic screen-share track is a small solid frame (320×180), enough to exercise a
  video forwarder but **not** bandwidth-representative of real 1080p screen content. A realistic capture source
  is needed before drawing screen-share bandwidth conclusions.
- **Config changes still required to exceed defaults** (each approval-gated, not part of P8.1):
  `LIVE_MAX_PARTICIPANTS_PER_SESSION` for the app-path >300/room, nginx `worker_connections`/
  `worker_rlimit_nofile` for >~6–7k clients, LiveKit `prometheus_port` for media metrics. The SFU-direct media
  path already bypasses the 300 app cap by design.

## Data isolation & cleanup

- **Media (SFU-direct):** tokens are minted directly and rooms use the `loadtest-` prefix, so the reconciler's
  prefix-scoped sweep ignores them and foreign-identity enforcement never runs on them (plan F7). **Zero app
  DB rows are created.** Cleanup: the harness deletes its rooms on teardown; a short `emptyTimeout` is a
  backstop.
- **API:** uses a disposable pre-seeded test account from `LOADTEST_API_*` — do not create accounts
  per-iteration (accounts have no hard delete). Never uses or notifies real users.
