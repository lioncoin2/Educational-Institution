# P8.2 — Off-box load generator + realistic screen source

**Date:** 2026-10-04. **Status: IMPLEMENTED + SMOKE-VALIDATED — no capacity load generated.** This phase
makes the P8.1 harness runnable from a separate machine, adds a read-only preflight, a realistic screen-share
source (resolves Q-P8-2), generator-side metrics, and validated the whole path with a **2-participant** smoke
test. It did **not** run the capacity ladder and changed **no** staging/runtime configuration.

> **OFF-BOX SMOKE TEST ≠ CAPACITY TEST.** The smoke here is 1 room / 2 participants / seconds, for
> connectivity and path validation only. The capacity ladder (10/100/…/3000/10000) is P8.3+, approved
> separately, and must run from a dedicated off-box generator.

## 1. Architecture

```
generator machine (separate Linux host — NOT staging)
  ├─ preflight  cli/preflight.ts → livekit/preflight.ts   (read-only checks → PASS/FAIL table)
  └─ run        cli/run.ts → safety gate (dry-run default)
                 ├─ livekit/tokens.ts   AccessToken (roomCreate) — signed locally, no server call
                 ├─ livekit/media-run.ts ─dynamic import─► test/livekit/load/media-driver.ts
                 │     listeners / audio speakers / screen (profiles) / forced relay
                 └─ metrics/generator.ts  GENERATOR-side CSV (this proc + its NIC + harness counters)
        │ public interfaces only (443, 7882/udp, 7881/tcp, 3478/udp)
        ▼
  staging VPS = SYSTEM UNDER TEST (unchanged)
        └─ metrics/collector.ts runs HERE, read-only, for SERVER-side CSV
```

Two metric collectors, deliberately separate: **generator-side** (`metrics/generator.ts`, runs on the
generator) and **server-side** (`metrics/collector.ts`, runs on staging). Mixing them is the classic
load-test mistake; a starved generator otherwise looks like a server limit.

The rtc-node boundary is unchanged: only `test/livekit/load/media-driver.ts` names the WebRTC client (now
also `@livekit/rtc-ffi-bindings` for `VideoEncoding`), kept under `test/livekit/` per the architecture test.

## 2. Generator machine requirements

- A **separate** Linux host (not the staging VPS). For the capacity ladder, several hosts with good upstream
  bandwidth and multiple cores (rtc-node spends real CPU per participant; the screen source especially).
- Node 22 + this repo checked out + `npm ci` (installs `@livekit/rtc-node` native bindings).
- Outbound reach to the staging public ports (below). No inbound ports needed.
- `LOADTEST_*` env exported locally (untracked). Nothing else from staging — no Docker, no DB/Redis, no
  filesystem, no control-plane access.

## 3. Staging target requirements

The staging VPS stays the system under test and is **not modified**. Public endpoints used:
`https://api-staging.adlink4.com`, `wss://livekit-staging.adlink4.com`. The LiveKit control API
(RoomService) is reachable through nginx at the https host — but SFU-direct runs use `roomCreate` tokens, so
no control-plane call is strictly required to create rooms off-box.

## 4. Network requirements

| Port | Proto | Purpose |
|------|-------|---------|
| 443 | tcp | WSS signalling + TURN/TLS (via nginx SNI) |
| 7882 | udp | LiveKit ICE/UDP media (direct path) |
| 7881 | tcp | LiveKit ICE/TCP fallback |
| 3478 | udp | TURN/UDP (relay + STUN) |

All are already open in the staging firewall from anywhere. The relay range 30000–32767/udp is internal to the
SFU host and is **not** opened publicly (relayed media reaches the client over 3478/443).

## 8. Screen profiles (resolves Q-P8-2)

`core/screen-profiles.ts` defines three profiles; the driver sets the encoder **bitrate ceiling** via
rtc-node `TrackPublishOptions.videoEncoding` (`maxBitrate`, `maxFramerate`) + `videoCodec = VP8`, and feeds a
deterministic **word-wise xorshift** pattern (high entropy) so the encoder sustains near the ceiling.

| Profile | Resolution | FPS | Codec | maxBitrate | Expected / publisher |
|---------|-----------|-----|-------|-----------|----------------------|
| SCREEN_360P | 640×360 | 15 | VP8 | 600 kbps | ~0.6 Mbps |
| SCREEN_720P | 1280×720 | 15 | VP8 | 1500 kbps | ~1.5 Mbps |
| SCREEN_1080P | 1920×1080 | 15 | VP8 | 2500 kbps | ~2.5 Mbps |

**What it represents / limitations (read before quoting bandwidth):** `maxBitrate` is a CEILING, not a
guarantee. The high-entropy content pushes the encoder toward the ceiling — an **upper bound** modelling a
*busy* share. Real desktop capture is mostly static (text/UI) and sits **well below** these numbers, spiking
on scroll/video. So these are worst-case planning figures; the achieved bitrate must be **measured**, never
inferred from resolution. The generated content has no semantic structure (it is noise), so it does not model
codec-specific screen-content optimizations (e.g. VP9 screen mode); it is a bandwidth stressor, not a visual
fidelity model. **Smoke measurement (SCREEN_360P):** LiveKit published the track at **640×360** with the
encoder at the **600 kbps ceiling** (simulcast layers 600k/150k) — confirming the control works.

## 9. TURN test

`smoke-relay` forces relay via rtc-node `rtcConfig.iceTransportType = TRANSPORT_RELAY`.

**Smoke result — relay engaged, with a labelling caveat:** both participants connected; the SFU's selected
remote candidates were on ports **30761 / 31070**, inside the TURN relay range (30000–32767) and *not* the OS
ephemeral range (32768+) — evidence the client's media egressed through the TURN relay allocation. However
LiveKit labelled `connectionType:"udp"` with a peer-reflexive (`prflx`) remote candidate, rather than
`"turn"`/`relay` as a browser did in P7.4 (the relay allocation was discovered as prflx, not signalled as a
relay candidate). **Interpretation:** relay via rtc-node appears to WORK at the transport level, but the
candidate labelling differs from the browser. Before the relay capacity rung (P8.3), confirm off-box on a
genuinely UDP-restricted network (where a direct 7882/udp path is impossible, so only relay can succeed) —
this smoke ran on-box, where a direct path is always available.

## 10. Metrics format

- **Generator CSV** (`metrics/generator.ts`): `t_ms, proc_cpu_pct, proc_rss_mib, gen_tx_mbps, gen_rx_mbps,
  active, connect_ok, connect_fail, publish_ok, publish_fail, subscribe_ok, subscribe_fail, reconnects,
  relay_ok, relay_fail`.
- **Server CSV** (`metrics/collector.ts`, runs on staging): `t_ms, tx_mbps, tx_pps, rx_mbps, udp_in_errors,
  udp_rcvbuf_errors, softnet_dropped, load1, mem_available_mib, conntrack, estab_conns, livekit_cpu,
  livekit_mem_mib, api_cpu, api_mem_mib`.

Both are plain CSV with a header row, one sample per interval (`--interval`, default 2 s), rates derived from
consecutive counters.

## 11. Safety limits

Unchanged from P8.1 and still enforced: dry-run default; real load needs `--allow-load` + `--target` +
within caps; hard caps (12,000 participants, 3,500/room, 200 rooms, 1,800 s, 200/s ramp, …); no `--force`.
The smoke scenarios are themselves capped at 2 participants / 1 room. Preflight generates no load at all.

## 12. What has NOT been tested yet

- **True off-box execution** — everything here ran *on the staging host* (no separate generator machine was
  available). On-box, media to the box's own public IP is local-delivery, so the generator NIC counters read
  ~0 and a direct UDP path always exists. The off-box path (DNS/TLS/nginx/ICE over a real network, generator
  NIC throughput, relay-only on a UDP-restricted net) is **unvalidated**.
- **Any capacity** — no run above 2 participants. No listener/room scaling, no multi-room, no sustained load.
- **Relay under restriction** — relay engaged on-box (relay-range ports) but was not proven on a network where
  the direct path is blocked (see §9).
- **Achieved screen egress bytes** — the encoder bitrate ceiling was confirmed applied; sustained real egress
  across many subscribers is a capacity-phase measurement.
- **API-plane load** — `LOADTEST_API_*` path is implemented but unexercised (no test account configured here).
