# P8.4 — Generator VM, agent interface, S-1 / S-2 and operator runbook

**Status:** Phase 1 implemented (HEAD + working tree, uncommitted). **Nothing below has been executed.**
The generator VM is supplied separately; S-1 and S-2 are SUT changes that each need explicit approval
before they are applied. Design: [p8.4-offbox-design.md](p8.4-offbox-design.md).

## 1. Generator VM requirements (exact)

| Item | Requirement |
|---|---|
| Count | 1 for S1, S2, R1, R2 and calibration; more only when design §16 shows they are needed |
| Identity | separate, disposable VM, different hardware from the SUT; **not** vmi3489812; runs nothing else |
| CPU / RAM / disk | x86_64; ≥ 16 vCPU (dedicated preferred); ≥ 64 GiB RAM (32 GiB is enough up to R2); ≥ 50 GB disk |
| OS | Ubuntu 24.04 LTS (glibc — `@livekit/rtc-node` ships `linux-x64-gnu`) |
| Kernel | Ubuntu generic kernel with NO_HZ active (the default; `nohz=off` must not be on the command line) — the exact CPU meter reads idle/iowait from the NO_HZ idle clock (D-12, errata E9) and a sampler on a `nohz=off` kernel refuses it, making every rung UNKNOWN |
| Packages | Node.js **22.23.x** + npm 10.9.x (same as the SUT), `git`, `iproute2` (`ss`, `tc`), `chrony` (clock offset for V-clock), `conntrack` (operator diagnostics) |
| Network | public **IPv4, no NAT**; IPv6 **not configured**; ≥ 1 Gbit/s; egress to 213.136.65.135: TCP 443, UDP 7882 (TCP 7881 allowed, not expected); egress to the npm registry for `install`; UDP 3479 bound locally by the in-process STUN responder |
| Inbound | TCP 22 from 213.136.65.135 only; nothing else |
| Time | chrony synchronised, offset < 10 ms (`chronyc tracking`) |
| Secrets | none — no LiveKit key, no SUT credential, no `infra/env/*.env` |

## 2. Bootstrap (run by the provisioner as root on the generator; not by the harness)

```sh
# user and directories — /opt/p84 root-owned with the sticky bit, so p84 can manage
# versions/ and the `current` link but can never rename or replace bin/
useradd --create-home --shell /bin/bash p84
install -d -o root -g p84 -m 1775 /opt/p84
install -d -o root -g root -m 0755 /opt/p84/bin
install -d -o p84  -g p84  -m 0755 /opt/p84/versions
install -d -o p84  -g p84  -m 0700 /var/lib/p84 /var/lib/p84/runs

# the dispatcher (from the approved commit: backend/test/load/fleet/bootstrap/p84-dispatch.sh)
install -o root -g root -m 0755 p84-dispatch.sh /opt/p84/bin/p84-dispatch

# limits
printf 'p84 soft nofile 65536\np84 hard nofile 65536\n' > /etc/security/limits.d/p84.conf

# firewall: SSH from the SUT only
ufw default deny incoming && ufw default allow outgoing
ufw allow from 213.136.65.135 to any port 22 proto tcp && ufw enable

# the SUT's P8.4 public key (from S-1), restricted to the dispatcher
install -d -o p84 -g p84 -m 0700 /home/p84/.ssh
printf 'restrict,from="213.136.65.135",command="/opt/p84/bin/p84-dispatch" %s\n' "$(cat p84_generator_ed25519.pub)" \
  > /home/p84/.ssh/authorized_keys
chown p84:p84 /home/p84/.ssh/authorized_keys && chmod 0600 /home/p84/.ssh/authorized_keys
# remove any temporary provisioning access before S1
```

Code is installed **from the SUT** (no push to any remote), through the dispatcher:

```sh
# on the SUT, from the repo at the approved commit
git -C /opt/Educational-Institution bundle create /tmp/p84.bundle HEAD
SHA=$(sha256sum /tmp/p84.bundle | cut -d' ' -f1)
ssh -i /root/.ssh/p84_generator_ed25519 -o UserKnownHostsFile=/root/.ssh/p84_known_hosts \
    -o StrictHostKeyChecking=yes p84@<GEN_IP> install "$SHA" < /tmp/p84.bundle
```

`install` verifies the bundle's SHA-256, clones it into `/opt/p84/versions/<sha>/repo`, runs
`npm ci --include=dev` in `backend/`, then switches `/opt/p84/current` atomically. The agent's
`hello` reports that SHA and commit; the controller refuses a mismatch with its own commit.

## 3. Agent interface

**SSH dispatcher** (`/opt/p84/bin/p84-dispatch`, the forced command; anything else exits 64):

| `SSH_ORIGINAL_COMMAND` | Effect |
|---|---|
| `agent <runId>` | `cd /opt/p84/current/backend && exec node -r ts-node/register/transpile-only test/load/fleet/agent-main.ts --run <runId> --runs-dir /var/lib/p84/runs` — NDJSON on stdio |
| `install <sha256>` | bundle on stdin → verify → clone → `npm ci` → switch `current` (exit 65 on hash mismatch, 66 if the version exists) |
| `fetch <runId>` | `tar` of `/var/lib/p84/runs/<runId>` to stdout (the SUT stores it and records its SHA-256 in the result) |
| `stop <runId>` | signals only the PIDs recorded in that run's `pids.json`, after verifying each PID's start time (PID-reuse safe); never its own process group |

`runId` = 16 lowercase hex; `sha256` = 64 lowercase hex; exactly two words.

**Protocol** (`p84-fleet/v1`, one JSON object per line; `fleet/protocol.ts`):

| Direction | Messages |
|---|---|
| controller → agent | `assign` (workers + settings), `admit` (one just-in-time ticket for one worker), `heartbeat`, `shutdown` |
| agent → controller | `hello` (protocol, commit, bundle SHA, Node, host facts), `ready` (worker count, STUN URL), `worker` (a worker event, verbatim), `exit` (worker exit, forced flag), `sample` (`p84-sample/v1`), `abort` (`p84-abort/v1` from the generator watchdog), `heartbeat`, `bye` |

The agent aborts on stdin EOF, SIGTERM/SIGINT/SIGHUP, or 10 s without a controller heartbeat
(dead-man), always through the same bounded stop path.

## 4. S-1 — SUT → generator control key (exact; requires approval)

```sh
# on the SUT (vmi3631989), as root
ssh-keygen -t ed25519 -N '' -C 'p84-controller@vmi3631989' -f /root/.ssh/p84_generator_ed25519
chmod 0600 /root/.ssh/p84_generator_ed25519
# once the VM exists: pin its host key, after comparing the fingerprint with the provider console
ssh-keyscan -t ed25519 <GEN_IP> > /root/.ssh/p84_known_hosts.candidate
ssh-keygen -lf /root/.ssh/p84_known_hosts.candidate
mv /root/.ssh/p84_known_hosts.candidate /root/.ssh/p84_known_hosts && chmod 0600 /root/.ssh/p84_known_hosts
```

Files created: `/root/.ssh/p84_generator_ed25519{,.pub}`, `/root/.ssh/p84_known_hosts`. The runner
also writes its evidence to `/var/lib/p84/results/<runId>/` (mode 0700) on each real rung.
**Removal after P8.4:** delete those three files and remove the key from the generator.

## 5. S-2 — nginx connection capacity (exact; requires approval; not applied)

Current `/etc/nginx/nginx.conf` lines 1–10 (verified 2026-10-04): `worker_processes auto;` and
`events { worker_connections 768; }`, no `worker_rlimit_nofile` (worker soft FD limit 1,024).

```diff
 user www-data;
 worker_processes auto;
+worker_rlimit_nofile 65536;
 pid /run/nginx.pid;
 …
 events {
-	worker_connections 768;
+	worker_connections 40960;
 	# multi_accept on;
 }
```

```sh
cp -a /etc/nginx/nginx.conf /etc/nginx/nginx.conf.p84-before-S2
# apply the two-line change above, then:
nginx -t && systemctl reload nginx
for w in $(cat /proc/$(cat /run/nginx.pid)/task/$(cat /run/nginx.pid)/children); do grep 'open files' /proc/$w/limits; done
nginx -T 2>/dev/null | grep -E 'worker_(connections|rlimit_nofile)'
# rollback
cp -a /etc/nginx/nginx.conf.p84-before-S2 /etc/nginx/nginx.conf && nginx -t && systemctl reload nginx
```

Why these values: design §15 (4 nginx connections per signalling WebSocket; the 10k worst case of
21,117 connections on one worker is 52% of 40,960). When it is needed: before R3 if the per-worker FD
share measured at R1/R2 (`nginx.perWorkerFdsAtGate`) projects the busiest worker above 60% of 768
(`P-proj`), otherwise before R4.

## 6. Operator runbook (after approval of each step)

```sh
cd /opt/Educational-Institution/backend
# dry-run: prints the plan and every cap check, generates nothing
npx ts-node test/load/cli/fleet-run.ts --rung S1 --generators <GEN_IP> --target wss://livekit-staging.adlink4.com
# S1 positive control (D-3), then the TURN-free S1 — one invocation each, never chained.
# Every rung after the control needs --previous <result of the rung before it>; a RED/UNKNOWN
# previous rung stops the ladder, a YELLOW one needs an explicit --accept-yellow.
npx ts-node test/load/cli/fleet-run.ts --rung S1 --ice relay --generators <GEN_IP> --target wss://livekit-staging.adlink4.com --allow-load
npx ts-node test/load/cli/fleet-run.ts --rung S1 --generators <GEN_IP> --target wss://livekit-staging.adlink4.com \
  --previous /var/lib/p84/results/<controlRunId>/result-S1-<controlRunId>.json --allow-load
npx ts-node test/load/cli/fleet-run.ts --rung S2 --generators <GEN_IP> --target wss://livekit-staging.adlink4.com \
  --previous /var/lib/p84/results/<s1RunId>/result-S1-<s1RunId>.json --allow-load
# emergency: stop the generators by recorded PIDs, delete the room, verify
npx ts-node test/load/cli/fleet-run.ts cleanup --run <runId> --generators <GEN_IP> --target wss://livekit-staging.adlink4.com
```

Exit codes: 0 GREEN (or a clean dry-run), 2 refused, 3 YELLOW, 5 RED, 6 UNKNOWN (also when a GREEN/YELLOW
rung's worker teardown was not clean). The nginx P-proj check runs on every rung from S2 using the previous
result's per-worker FD evidence; the rest of the 10k checklist (design §14: hottest-core fit over R3–R5, TX
projection, per-host fleet load) is an operator review of the attached R3–R5 results, not yet automated. Each rung writes
`/var/lib/p84/results/<runId>/result-<rung>-<runId>.json` (`p84-rung-result/v1`), the event CSV,
per-host sample NDJSON and the fetched generator archive, each with its SHA-256 in `evidence`.
