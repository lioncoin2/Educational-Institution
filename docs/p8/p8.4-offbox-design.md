**As built — deviations from the approved plan (each deliberate):**
1. The dispatcher is a root-installed POSIX shell script, not `fleet/dispatch.ts`, so `p84` cannot alter
   the allowlist. `fetch` streams a tar without a size cap; its SHA-256 is recorded on the SUT in the result.
2. There is no `fleet-run --local`: the local fleet (real controller + local agents + fake driver) is
   exercised only by the jest integration tests, so the operator CLI carries no test scaffolding.
3. `metrics/generator.ts` is retained (single-process path); `partitionParticipants` was not reused (§4).
4. Generator rules are judged only after warm-up (a previous sample and a worker lag report exist);
   observations count only inside the hold and the 15 s lookback before a trigger, so process start-up
   (spawn, ts-node compile) is never misread. An agent that was never judged fails V-sampler (fail closed).
5. V-sampler also covers harness integrity: out-of-scope agent reports, identities on the SFU that nobody
   minted, and controller errors (verdict table updated).
6. The result carries `cleanup.teardown` (P8.3.8 classes); `fleet-run` never exits 0 when teardown was
   not clean. `M-unbound` (post-rung `track not bound`) feeds the verdict; a missing LiveKit log fails closed.
7. A negative `packetsLost` step is not a sampler gap (it is an estimate that legitimately steps down);
   only `packetsReceived` going backwards is a reset.

## 2. Credential flow

```
SUT controller                                                generator agent → worker
  parse ONLY LIVEKIT_API_KEY/SECRET from infra/env/staging.env into a local object (never process.env)
  runId = fresh CSPRNG (≥ 64 bits); room = loadtest-p84-<runId>
  ListRooms([room]) must be empty → CreateRoom(room, maxParticipants=N) on 127.0.0.1:7880
  per ramp credit: mint ticket(identity, room) ──ssh──▶ {url, token} ──IPC──▶ connect (token in header)
  end: DeleteRoom → every session closed; tickets cannot re-create the room
```

**Grants** (via `livekit/tokens.ts`):

| Grant | Listener | Publisher |
|---|---|---|
| `roomJoin` / `room` | true / `loadtest-p84-<runId>` | same |
| `canSubscribe` | true | false |
| `canPublish` / `canPublishSources` | false / `[]` | true / `[MICROPHONE]` |
| `canPublishData`, `canUpdateOwnMetadata` | false | false |
| `roomCreate`, `roomAdmin`, `roomList`, `roomRecord`, `ingressAdmin`, `agent` | absent | absent |
| `hidden` | false (production-faithful; D-5) | false |
| `sub` / initial TTL | one identity per ticket, minted at most once per run / 300 s | same |

**Properties — mechanism — evidence** (LiveKit v1.13.7; rust-sdks `livekit-ffi/v0.12.73`):

| Property | Mechanism | Evidence |
|---|---|---|
| Secret never leaves the SUT | parsed into the controller only; every spawn gets an **exact env allowlist** (set-equality test over every spawn site); never in argv/logs/channel; the `git bundle` cannot contain it (`infra/env/*.env` git-ignored, `infra/.gitignore:3`) | unit tests |
| Short-lived | **Join tickets: 300 s**, minted just in time per ramp credit. **Once joined, LiveKit refreshes the participant's token at join and every 5 min, valid max(10 min, remaining)** with the same grants — so a connected generator holds ≥ 10-min session tokens | `pkg/service/roommanager.go:60-63, 764-765, 1153-1166`; rust `rtc_session.rs:1500-1502`; rtc-node `TokenRefreshed` |
| Revocable by ending the test | `DeleteRoom` closes every session; refreshed tokens cannot re-create the room because they lack `roomCreate` and `auto_create: false`; the room name is never reused (fresh `runId`, empty `ListRooms` check) | `roomallocator.go:175-183`, `auth.go:197-203` |
| Room-scoped / no unrelated rooms | `room` claim; no `roomAdmin`/`roomList`/`roomCreate` → every RoomService call is denied | `auth.go:169-211` |
| Identity-scoped | one `sub` per ticket. **A second join with the same identity evicts the holder** (`removing duplicate participant`, `ParticipantCloseReasonDuplicateIdentity`); detected and the rung is invalid (`V-dup`) | `roommanager.go:399-400` |
| Cannot exceed N | `CreateRoom maxParticipants = N` | `pkg/rtc/room.go:457-467` |

**Residual exposure (stated, not hidden):** each join response also carries per-participant credentials
for the SUT's shared TURN service (valid for LiveKit's TURN TTL, independent of the ticket TTL). The
TURN-free client never uses them, live abort rules catch any relay use (§17), and the disposable VM is
destroyed after P8.4. RoomService is **publicly reachable** through the `livekit-staging` vhost
(443 → 8443 → 7880, `location /`); tickets are refused there by the grant checks above. The controller
itself always uses loopback `http://127.0.0.1:7880` (hard-coded, not overridable).

**Phase 1 verification on a *local* LiveKit test server (never the SUT):** join another room → denied;
join after delete → denied; RoomService with a ticket → denied; (N+1)-th join →
`ErrMaxParticipantsExceeded`; duplicate identity → evicted with the recorded reason; `TokenRefreshed`
received, its `exp` ≥ 10 min, grants unchanged.

## 3. Generator fleet architecture

- **Access model:** one restricted key for the whole lifecycle —
  `restrict,from="213.136.65.135",command="/opt/p84/bin/p84-dispatch"` in `p84`'s `authorized_keys`.
  `p84-dispatch` (not writable by `p84`) allows exactly: `agent <runId>` (NDJSON control on stdio),
  `install <sha256>` (git bundle on stdin, verified against the controller-announced hash, unpacked into a
  new versioned directory, then `npm ci`), `fetch <runId>` (tar of that run's fixed directory to stdout,
  size-capped, with a SHA-256 manifest), `stop <runId>` (signals only PIDs recorded in that run's file).
  No provisioning key is kept after setup; emergency fallback is the provider console / VM destroy.
- The **SUT** stores the generator's host key in a dedicated `known_hosts` file (part of S-1).
- **Handshake** (`hello`): protocol version, installed bundle SHA-256 and commit, `package-lock.json`
  hash, Node version, vCPU/RAM/NIC/IPv4, clock offset. The controller refuses any mismatch. (The SHA is
  self-reported, so it detects mistakes, not a compromised generator — §7's server-side checks cover
  that.)
- **Untrusted input:** the controller validates every message against the schema with a maximum line
  length, and rejects any event whose identity was not minted to that agent's shard.
- **Heartbeats** every 2 s both ways. **Dead-man:** an agent aborts and tears down after 10 s without a
  controller heartbeat or on stdin EOF; the controller declares an agent lost after 10 s → fleet abort.
- **Event volume:** lifecycle transitions and failures are discrete events; media stats travel as
  per-worker 5 s aggregates; raw per-participant samples stay on the generator (NDJSON) and are pulled
  with `fetch` after the rung.
- **Processes:** the agent's process manager owns every worker; the STUN responder and host sampler are
  in-process (no hidden background processes); teardown is IPC `shutdown` with the P8.3.8 bound; forced
  kill targets recorded child PIDs only.

## 4. Participant sharding

- A **shard** = (agent `a`, worker `w`) with a contiguous global index range `[start, end)` assigned by
  the controller. Identities `p84-<run8>-L<index:05d>`, publisher `p84-<run8>-P0`, room
  `loadtest-p84-<runId>` (the `loadtest-` prefix keeps the app reconciler away, plan F7).
- Ranges are disjoint and cover exactly N−1 listeners (`fleet/shards.ts`, property-tested: no overlap,
  no gap, deterministic). The global shard index is the `workerId` used by the single aggregator.
- **No worker or agent can delete the room** — they hold no RoomService credential at all.
- Density and processes per host are parameters bounded by per-rung caps (§14) and measured values (§16).

## 5. Publisher ownership

- The controller owns the publisher identity and ticket and places it on a **dedicated worker process**
  on agent 1 (no listeners in that process).
- Publish options are set **explicitly**: `dtx = false` (a continuous tone must never pause), RED as
  observed today (`audio/red`, errata E8). The profile records both.
- **Phase A** (before any listener ticket exists): `connecting → connected → publishing → published`
  (existing `PublisherState`), then (1) server side: `ListParticipants` shows the publisher with exactly
  one audio track (SID recorded); (2) client side: `outbound-rtp packetsSent` rises over two consecutive
  windows at the expected rate.
- **Hold:** rule `M-pub`.

## 6. Global ramp

- The controller runs a **token bucket at R participants/s**; each token *is* a ticket (minting =
  admission), so pacing, just-in-time TTL and the global rate are one mechanism. Today's per-supervisor
  `rampStaggerMs` (with its 250–3000 ms clamp distortion) is retired.
- The bucket's clock starts at its **first grant** (the start of phase B), full at `burst`: time spent in
  phase A never becomes credit. The reported `rampRate.actual` is the measured inter-admission rate,
  (listeners − 1) ÷ (last − first ramp **grant**), null below two listeners — grant times, because issue
  stamps follow the mint, whose latency (a cold first JWT signing) compresses the span.
- **Concurrency has one owner:** the controller keeps in-flight accounting per shard (ticket issued, no
  terminal event yet) and issues the next ticket to the shard with the most remaining work below its
  in-flight limit (default 4). Workers admit each ticket immediately.
- **Rate:** default target **10/s**. This was the *configured* P8.3.7 rate; the *measured* on-box join
  rates were only ≈3/s (rr100) and ≈5/s (MP_40). S2/R1 are the first real check of 10/s; the Phase B
  timeout uses the measured rate (`P-gate`).
- **Measured per participant:** ticket issued (controller clock) → connected → subscribed → first packet
  (agent clocks, offsets recorded). Actual rate = sliding 10 s window of `connected`.
- **Ramp-induced vs steady-state:** rule `V-ramp` (UNKNOWN). Connect errors carry their reason; any
  LiveKit/nginx rejection evidence for the failed identities makes it RED (class B/E) instead. A re-run at
  R/2 needs approval; never automatic.

## 7. Exact-N gate (global)

The hold starts only when all of these hold at once, computed by the controller:

1. `connected == N`, `failed == 0`, worker crashes `== 0`;
2. **server-side identity check:** loopback `ListParticipants` returns **exactly** the minted identity set
   (no extras, none missing), all `ACTIVE`, the publisher with exactly one audio track;
3. publisher `published` and server-confirmed (§5);
4. media gate (§8): `subscribed == receiving == N−1`;
5. transport proof per participant (§17 T2) and no live validity abort;
6. no RED rule active.

Timeouts: `P-gate`. The server-side identity check is repeated at hold end; a mismatch → class F,
UNKNOWN. On timeout or any failure: global abort (§20).

## 8. Media-delivery gate

**Signals** (raw from `media-driver`, judged by the pure `mp/media-health.ts`):

| Signal | Source |
|---|---|
| subscribed to the publisher's audio | `TrackSubscribed` for the publisher's track SID |
| received | `inbound-rtp packetsReceived > 0` from `getRtcStats()` |
| still subscribed/connected | no `TrackUnsubscribed`, `TrackSubscriptionFailed`, `Disconnected` (with `DisconnectReason`), `ParticipantDisconnected` for the publisher; `ConnectionStateChanged` |
| not silently losing media | stall rule `M-stall`; per-listener loss bands `M-loss-listener` |
| quality (recorded) | `packetsLost`, `jitter`, delivery ratio (`M-detail`) |

- **Stall definition:** Δ`packetsReceived` = 0 between two *successful* stats samples whose stats
  timestamps are ≥ 5 s apart, cross-checked with `lastPacketReceivedTimestamp` where the bindings expose
  it. A **missing or late sample is a sampler gap** (validity `V-sampler`, generator class A), never a
  stall. `getRtcStats()` calls are staggered across a worker's participants.
- **Minimum media-health criterion** (binary, no invented loss number): through the whole hold every
  listener is subscribed and connected with no stalled window; zero disconnects/unsubscribes; after the
  rung, zero `track not bound after timeout` for the run room (`M-unbound`, which would have caught
  errata E3). Loss bands are the plan's, applied **per listener and fleet-wide**, and stay
  **provisional** until validated against the off-box baseline (verdict table).
- **False-stall validation:** the stall rule's false-positive rate is measured over ≥ 1,800
  listener-windows at R1/R2 before R3 (S1/S2 alone are too small).
- **Content probe (sampled):** one listener per agent consumes an `AudioStream`; the pure Goertzel
  detector (`mp/tone-probe.ts`) checks 440 Hz energy — proof that decoded audio arrives. It judges the
  **median of per-100 ms block ratios** over 1 s (each block phase-coherent): receive-side playout shifts
  the tone's phase, which a single 1 s coherent window mistakes for missing audio. The publisher feeds
  the tone by awaiting each `captureFrame` (the SDK's real-time backpressure), never a JS timer. Its CPU
  is reported separately.

## 9. Watchdog

| Layer | Runs | Reads | Raises |
|---|---|---|---|
| **SUT** | in-process in the controller | per-core `/proc/stat`; `/proc/net/{snmp,snmp6,softnet_stat,dev}`; `/proc/meminfo`; `/proc/vmstat`; conntrack count; **per-socket drops via `ss -uanm` (sock_diag)** for every 7882 bind and 3478 (on this host the 7882 sockets do not appear in `/proc/net/udp*` and 3478 is a dual-stack v6 socket); relay-range sockets via `ss` (udp + udp6); `tc -s qdisc show dev eth0`; read-only `iptables/ip6tables -L ufw-user-input -v -x` new-flow counters for 3478/7882; LiveKit PID `/proc/<pid>/{stat,status,fd}`; nginx worker FD counts; ESTAB counts on 127.0.0.1:8444/5349; container restart counts + LiveKit health; nginx error-log tail | abort → controller |
| **Generator** | in-process in each agent | the same host signals for its VM, event-loop lag, its process group, egress flows to SUT:3478 | abort → controller; local dead-man |
| **Controller** | — | gate, media and fleet state | global abort |

- **Rules are data** (`observe/rules.ts` = the verdict table, each rule with `id` and `classHint`);
  evaluation is pure (`observe/watchdog.ts`) with the table's sampling semantics; fixture-tested.
- **Fail closed:** before each rung the sampler asserts the expected sockets exist (4 × 7882, 1 × 3478)
  and every reader works; a missing source is `V-sampler`, never a silent zero.
- **Abort pipeline:** rule fires → abort record → global abort → agents stop admitting and send
  `shutdown` → P8.3.8 bounded teardown → controller `DeleteRoom` → cleanup verification → result
  (classification per the verdict table: safety abort is recorded separately from the verdict).
- **Abort reason** (`p84-abort/v1`): `{ runId, rung, at, source: "sut-watchdog"|"gen-watchdog:<host>"|
  "controller"|"operator", rule, observed: { value, unit, samples[] }, threshold: { ruleId, op, value,
  sustain }, classHint }`.
- **Safety:** recorded PIDs only; process-group kills only when `pgid ≠ own pgid`; SIGTERM/SIGINT in the
  controller, agent and worker all enter the same abort path; a worker treats IPC `disconnect` as
  shutdown (closes errata E5's orphan gap).
- **Post-rung only:** LiveKit log analysis (≈21 KB logged per join) runs after the hold over the rung's
  `--since/--until` window (`observe/livekit-log.ts`), so it never loads the SUT during measurement.

## 12. Cleanup

Owned by the controller (`fleet/cleanup.ts`), in this order, on success or abort:

1. Stop admission. 2. Broadcast `shutdown`; workers run the P8.3.8 bounded teardown; agents report
`TeardownSummary` + process accounting and exit; the controller checks each SSH session's exit status.
3. `DeleteRoom` (loopback).
4. **Verify** (each a result field): RoomService — 0 rooms named for the run, 0 `loadtest-` rooms,
0 participants; DB — read-only `count(*)` of load-test rows = 0, run as a recorded short-lived child
(`docker exec institution-db-1 psql -tAc …`, as P8.3 did) so the controller never loads a DB
credential; generator — 0 live children per agent; SUT — 0 relay-range sockets, 0 TURN/TLS ESTAB;
recovery — `P-rec-ct`, `P-rec-cpu`, `P-rec-miss`.
5. Fetch generator artifacts (`fetch <runId>`), record their SHA-256, write the result.

Rooms/participants/DB rows/generator processes not zero → **RED, and the next rung may not start**.
`fleet-run cleanup --run <runId>` re-runs steps 3–4 idempotently (emergency, §20).

## 13. Failure classification (A–G)

| Class | Meaning | Decisive evidence |
|---|---|---|
| **A** generator | the fleet limited the run | any `G-*` rule; drops counted on the generator (UDP/softnet/qdisc/NIC); a sampler gap on a generator |
| **B** LiveKit/SFU | LiveKit misbehaved while the host had headroom | `S-lk-health`, LiveKit restart, rejections in connect errors/logs, `M-stall`/`M-unbound` with every `S-*` and `G-*` GREEN |
| **C** SUT host | host resources | `S-cpu-hot`, `S-mem`, `S-oom`, `S-load`, `S-swap` |
| **D** network | packets lost between hosts | drops counted at the SUT edge (`S-udp`, `S-sock7882`, `S-softnet`, `S-qdisc`, `S-nic`) or `S-tx`; or packets missing with **no** drop counted at either end (path loss, provider shaping suspected) |
| **E** infrastructure | edge/kernel limits outside LiveKit | `S-ngx-*`, `S-ct`, TLS/DNS, a non-LiveKit container restart |
| **F** harness defect | our code | protocol/schema error, aggregate inconsistency, server identity set mismatch, `V-dup` from a harness bug, sanity failure |
| **G** application path | app-only limits | path B only; never in this ladder |

**Rules.** Attribution compares **packets, not bytes**, and looks at *where* drops are counted (generator
side → A; SUT side → C or D-at-SUT; neither → D-path). With H ≥ 2, loss concentrated on one host points
to that host or its path. Classification evaluates **all** rules over [first trigger − 15 s, trigger],
not just the first instant rule to fire (a slow cause like `G-cpu` must not lose to a fast symptom like
`M-stall`). The primary class is the earliest *cause*; others are contributing. Conflicting evidence →
UNKNOWN with both classes listed. No class without its evidence fields.

## 15. nginx capacity calculation

**Chain (verified):** client TLS → `443` stream server (`ssl_preread`, `listen 443 reuseport` → 18
sockets) → `127.0.0.1:8443` http server (TLS terminate; one listen socket, no `reuseport`) →
`127.0.0.1:7880`. Per signalling WebSocket nginx holds **4 connections** (stream downstream + upstream
in worker W1 chosen by the `reuseport` hash; http downstream + upstream in worker W2, whichever wins the
8443 accept). Each is one FD and one `worker_connections` slot. TURN/TLS (443 → 8444 → 5349) would add
4 more per client; in TURN-free mode it is 0, checked by T7. One WebSocket per participant; the
controller's RoomService calls use loopback 7880 and bypass nginx.

**Current limits (verified):** `worker_processes auto` = 18; `worker_connections 768` → 13,824 slots;
no `worker_rlimit_nofile` → worker FD soft limit **1,024** (hard 524,288). Fixed overhead ≈ 6 slots and
≈ 40 FDs per worker (estimate: listeners, channels, logs, epoll).

| N | WS | nginx conns = FDs (4N) | Total nginx FDs (4N + 18×40) | Balanced per worker (+6) | vs 768 | Worst case: every 8443 accept on one worker (2N + 2N/18 + 6) |
|---|---|---|---|---|---|---|
| 1,000 | 1,000 | 4,000 | 4,720 | 228 | 30% | 2,117 ✗ |
| 3,000 | 3,000 | 12,000 | 12,720 | 673 | **88%** | 6,339 ✗ |
| 5,000 | 5,000 | 20,000 | 20,720 | 1,117 | **145% ✗** | 10,562 ✗ |
| 10,000 | 10,000 | 40,000 | 40,720 | 2,228 | **290% ✗** | 21,117 ✗ |

The real 8443 accept distribution is unknown (EPOLLEXCLUSIVE wake-ups are not round-robin), so even
1,000 is not guaranteed today. Per-worker FD counts are sampled from R1 (`S-ngx-share`); the measured
busiest-worker share drives `P-proj`.

**Smallest safe change** (one file outside the repo, two directives, graceful reload; **approval S-2**):

```nginx
# /etc/nginx/nginx.conf
worker_rlimit_nofile 65536;          # main context: ≥ worker_connections + overhead; ≤ hard 524288
events { worker_connections 40960; } # 10k worst case 21,117 = 52% → GREEN on S-ngx-share
```

- Why 40,960: it keeps even the worst-case distribution at 10k inside `S-ngx-share` GREEN (< 60%), so R6
  never needs a second nginx approval. (32,768 would put the worst case at 64% — YELLOW — and fail
  `P-proj`.) The alternative, 16,384 plus `reuseport` on the 8443 listen, touches the repo-tracked site
  config and relies on balancing; it is the fallback only if the memory check fails.
- Cost: nginx pre-allocates ≈ 0.4–0.5 KiB per slot (connection + two events) → ≈ 16–20 MiB per worker,
  ≈ 0.3–0.36 GiB total (estimate; verified by worker RSS after reload).
- Procedure: snapshot `nginx.conf` → edit → `nginx -t` → `systemctl reload nginx` (graceful) → verify
  `/proc/<worker>/limits` and `nginx -T`. Rollback: restore the snapshot → `nginx -t` → reload.
- Other limits: each loopback hop needs N source ports per destination (10k = 35% of 28,232); LiveKit
  FD limit 524,287; listen backlog 511 and `somaxconn` 4,096 are ample at 10/s.

**conntrack (model; measured from R1):** per participant ≈ 3 TCP (public 443 + two loopback hops) + ≥ 1
UDP + possible ICE/TCP attempts → ≈ 4–6 entries → 40–60k at 10k (15–23% of 262,144). The on-box
≈ 63/participant included TURN and on-box routing and is not used.

## 16. Generator sizing methodology

**Known (upper bounds only):** ≈ 450 MiB RSS per 10-participant worker process, ≈ 31 MiB per
participant (on-box, summed VmRSS). **Unknown:** CPU per participant (errata E4), per-process safe
density (RUNG-1 failed near 40 in one process on-box), and how per-participant cost grows with room size
(visible listeners each process every other participant's updates: O(N) per participant, O(N²)
fleet-wide).

**Method — measurement-gated; no functional form is trusted until it is tested:**

1. **Sanity (S2):** host CPU from `/proc/stat` deltas; per-process CPU = Δ(utime+stime) ÷ (CLK_TCK × wall
   s); Σ processes ≤ host busy or the rung is UNKNOWN (`V-sampler`, fixes E4 in code with unit tests).
2. **Cost points (R1, R2), one VM, d = 10:** CPU core-s/s, RSS, NIC bps **and pps**, hottest core and
   softirq, event-loop lag — per participant and per process.
3. **Density:** sweep d ∈ {10, 20, 30} at N = 100 (stop at the first failure or any `G-*` YELLOW), then
   **confirm the chosen d\* at N = 300** before R3 — density measured at both sizes, as decided (B9).
   Each sweep run is a separate approved calibration run (D-9).
4. **Calibration point:** one more single-VM point before R3 (e.g. N ≈ 600) if RSS allows, so three room
   sizes exist. Only then are linear and quadratic fits compared (residuals reported); projections use
   the **upper envelope** of both, and are tagged as projections.
5. **Envelope rule** (`P-step`): grow horizontally so per-host participants, per-process density and
   per-host ingress pps never exceed values already observed GREEN by more than the allowed step.
6. **Host count** (`P-host`) from the largest GREEN rung's measured costs; hottest core and pps are
   sized, not just total CPU. Add hosts *before* the rung.
7. **Live check:** d\* is re-verified on one host during the first ramp seconds of each rung; any `G-*`
   YELLOW or RED → UNKNOWN (class A); add capacity and rerun only with approval.

Illustration only (not a plan): at the RSS upper bound and d = 10, 1,000 participants ≈ 45 GiB of worker
RSS; a 10k fleet could need several large VMs. Step 3 can change this materially.

## 17. TURN-free proof methodology

**Mechanism (test-scoped; production TURN untouched).** Direct mode passes an explicit, **non-empty,
TURN-free** ICE-server list: `rtcConfig = { iceTransportType: TRANSPORT_ALL, continualGatheringPolicy:
GATHER_CONTINUALLY (SDK default), iceServers: [ { urls: ["stun:<generator-ipv4>:3479"] } ] }`. The bundled
SDK merges the server's ICE servers (which include TURN) **only when the client list is empty**
(rust-sdks `livekit-ffi/v0.12.73`, `rtc_session.rs:2547-2558`) — exactly what caused errata E2. The
server's `force_relay` client setting would override; the SUT sets none (checked in Phase 1 from the
join response).

**STUN endpoint:** an in-process RFC 5389 Binding responder in each agent (`fleet/stun.ts`, owned and
closed by the agent). It is a real STUN server, contacts no third party and never touches the SUT. The
generator has a public IPv4 with no NAT, so host candidates suffice; STUN keeps the list non-empty and
correct. (Fallback: a public STUN server — fewer moving parts, third-party dependency.)

**Proof — every check per rung; any failure → `V-turn` (UNKNOWN):**

| # | Evidence | Side | Notes |
|---|---|---|---|
| T1 | The applied ICE configuration contains no `turn:`/`turns:` URL | client | our input |
| T2 | No `relay` local candidate gathered; every selected pair is **udp**, local type ∈ {host, srflx, prflx}, remote port = the SUT's LiveKit UDP port (parameter; 7882 on the SUT) | client | |
| T3 | `participant active` shows `connectionType=udp` for every run identity; no `relay` remote candidate in `ice reconnected or switched pair` | server log | supporting |
| T4 | 0 `TURN allocation quota reached` for run identities | server log | supporting only: successful allocations are not logged at info level |
| T5 | 0 UDP sockets (udp + udp6) in 30000–32767 in every sample | SUT `ss` | relay sockets |
| T6 | 3478 traffic: delta of the read-only ufw `udp dpt:3478` **new-flow** counters (`iptables`/`ip6tables -L ufw-user-input -v -x`, host-wide) stays within the pre-rung background rate, **and** the generator-side egress flow count to SUT:3478 = 0 | SUT + generator | host-wide counter (internet scanners also hit 3478), so attribution comes from the generator side. The drop counter is *not* used (it moves only on overflow) |
| T7 | 0 ESTAB on 127.0.0.1:8444 and 127.0.0.1:5349 in every sample (host-wide), and each generator's TCP connections to SUT:443 = its live participants | SUT + generator | 5 s sampling may miss a sub-5 s connection; the generator-side count closes that gap for our traffic |

**Live abort (not only post-rung):** from the first ramp credit, any client reporting a relay local
candidate or a TURN URL, any relay socket (T5), or any generator flow to SUT:3478 aborts the fleet
immediately (`V-turn`) — an E2-style regression cannot hold relays for a whole ramp.

**Positive control (S1 only; approval D-3):** before the TURN-free S1, one participant connects in the
existing forced-relay mode for 10 s. Expected to move: T1 (TURN URL present), T2 (relay candidate
selected), T5 (relay socket), T6 (new 3478 flows from the generator). Not expected to move: T4 (no quota
hit with one client) or 3478 drops. If an expected detector does not move, the proof method is wrong and
P8.4 stops.

**Local tests (Phase 1):** the local LiveKit test servers have no TURN, so they cannot show TURN being
excluded — `iceServers: []` would pass there too. They check the client side only (applied config has no
TURN URL, no relay candidate gathered). The first proof that TURN is excluded is S1 on the SUT.

The generator is IPv4-only, so media is IPv4; the SUT samplers still read IPv6 (`snmp6`, udp6) to prove
it.

## 20. Rollback / abort strategy

| Level | Trigger | Action | Bound |
|---|---|---|---|
| **Soft abort** | any RED rule, live validity abort, gate failure, operator Ctrl-C/SIGTERM | stop admission → `shutdown` → bounded teardown → `DeleteRoom` → verify → result | teardown 7 s per worker, grace 10 s (P8.3.8) |
| **Hard abort** | worker past grace; agent unresponsive | process manager SIGKILLs recorded children (recorded as `forced`); controller closes the SSH session | +5 s |
| **Dead-man** | controller or SSH lost | agent self-aborts after 10 s without heartbeat / on stdin EOF | 10 s |
| **Emergency (operator)** | controller dead | SUT: `fleet-run cleanup --run <runId>`; generator: `ssh … stop <runId>` (dispatcher signals recorded PIDs only); last resort: provider console / destroy the disposable VM | runbook |

Guarantees: one abort path for every trigger; no automatic retry or escalation; every abort yields a
result with `verdict`, `validity` and `safetyAbort`; only the controller (or the emergency command)
deletes the room. **SUT config rollback:** the only SUT config change in scope is S-2, with a snapshot and
a one-command rollback.
