# P8.3 errata — corrections found by the P8.4 Phase 0 audit

**Date:** 2026-10-04 · **Found by:** P8.4 Phase 0 read-only off-box audit (HEAD `0caba62`) ·
**Status:** recorded; corrections drive the P8.4 design ([p8.4-offbox-design.md](p8.4-offbox-design.md)).

This page corrects conclusions reported during P8.3.5–P8.3.8. Earlier documents and commits are **not
rewritten**; this page is the authoritative correction and is referenced from
[`../p8-load-capacity-plan.md`](../p8-load-capacity-plan.md) by a one-line pointer (approved D-10).
Every P8.3 run was **ON-BOX** (generator on
the SUT), so none of its numbers were ever authoritative for NIC/softirq capacity — the items below are
errors *beyond* that known limitation.

## Summary

| # | What P8.3 said or implied | What is actually true | Consequence |
|---|---|---|---|
| E1 | P8.3.7's first 100-run aborted on UDP receive-buffer errors on the media path | All 179 UDP receive-buffer errors were on the **TURN socket `*:3478`**, not on the media socket 7882 | The thundering-herd trigger stands, but the overflowing socket was TURN |
| E2 | "Direct" mode (`--media-path direct`) was TURN-free | Direct-mode clients **allocated TURN relays on the SUT**; the selected media path was almost always direct UDP (at least one session used ICE/TCP) | No P8.3 run was a clean "no TURN" measurement |
| E3 | The exact-N gate (N/N connected) meant N participants in the call | It meant N **signalling connections**. A gate-passing run had a listener that **never received the publisher's audio** | P8.3 "N/N" results prove connection and teardown, not media delivery |
| E4 | P8.3.7 measured generator CPU (≈888% avg for 100 participants) | That metric was **invalid** (it exceeded the whole host's busy CPU) | All P8.3 generator CPU-per-participant figures are void |
| E5 | "A PID/process-group scoped watchdog exists" | The watchdog was an **ad-hoc, uncommitted shell script**; it was not preserved | No repo code enforces any stop threshold |
| E6 | (Implied) the harness could be scaled out | **Multi-host coordination never existed**: one supervisor + local forked workers | Off-box fleets cannot use the P8.3 harness unchanged |
| E9 | Host-wide busy CPU from `/proc/stat` is the host's CPU use (and the reference E4 compared against) | On this kernel `/proc/stat` busy is **tick-sampled** and under-reads exact task runtime by **25–50 %** for short, timer-driven bursts; per-process `utime+stime` are exact (*added 2026-10-04, P8.4 pre-commit real validation*) | P8.3 host-busy % figures are **lower bounds**; E4's conclusion stands on other grounds; P8.4 checks E4 and its CPU rules against exact busy (*first `/proc/schedstat`, superseded 2026-10-05 by the NO_HZ idle clock — addendum*) |

Two documented **plan** figures are also corrected (E7, E8).

## Details and evidence

### E1 — the 179 UDP drops were on TURN 3478, not media 7882

- Evidence (2026-10-04, `ss -uanm`): `*:3478 … skmem:(…rb212992…d179)` — the only UDP socket with drops;
  every 7882 socket (`213.136.65.135`, `[2a02:…]`, `172.17.0.1`, `172.30.0.1`) shows `rb33554432 … d0`.
  Host `Udp RcvbufErrors/InErrors` = 179/179 = exactly the 3478 socket's `d179`.
- The 3478 socket uses the kernel default receive buffer (208 KiB); the media socket has 32 MiB.
- P8.3.7's diagnosis "all listener workers forked at once → burst" remains the **trigger**. The fix
  (global ramp pacing) remains valid. What changes is the mechanism: the burst overflowed the **TURN**
  socket because direct-mode clients were contacting TURN (E2).
- Consequence for P8.4: UDP drop counters must be **attributed per socket**. On this host the 3478
  socket is dual-stack and appears only in `/proc/net/udp6`, and the LiveKit 7882 sockets do not appear
  in `/proc/net/udp` or `/proc/net/udp6` at all — so per-socket drops are read via sock_diag
  (`ss -uanm`), with a fail-closed check that every expected socket is present. A drop counter moves only
  on buffer overflow, so TURN *use* is detected separately (design §17).

### E2 — "direct" mode was not TURN-free

- Evidence: LiveKit logged **336** `TURN allocation quota reached` events from **161** distinct
  direct-mode participants (rr100 at 14:26 UTC: 74 events / 31 participants; P8.3.8 ladder at
  14:57–14:58 UTC: 52 / 26). Almost all selected media pairs were still direct to the SFU — udp4 228,
  udp6 164 — but at least one direct-mode session selected **tcp6** (ICE/TCP 7881). The relays were
  allocated but not selected for media.
- Root cause (verified in source): direct mode passed **no `rtcConfig`**, so the client ICE-server list
  was empty. The LiveKit Rust SDK bundled in `@livekit/rtc-ffi-bindings` 0.12.73 then **adds the
  server-provided ICE servers, including TURN** (`rust-sdks`, tag `livekit-ffi/v0.12.73`,
  `livekit/src/rtc_engine/rtc_session.rs:2547-2558`: `if config.ice_servers.is_empty() { … push server
  ice_servers … }`).
- Also corrects plan finding **F2** ("Direct-UDP clients are unaffected" by the relay range): direct
  clients do consume TURN allocations unless their ICE-server list excludes TURN.

### E3 — connected count did not prove audio delivery

- Evidence: P8.3.8 `MP_40` reported `connected 40/40, gateMet: true`, yet LiveKit logged
  `track not bound after timeout` for `MP_40-r0-listener-21` **7 times, every ~3 s from 14:58:50 to
  14:59:08 UTC**, i.e. through the whole hold (connected 14:58:28–14:58:38, teardown 14:59:08).
  `MP_SMOKE-r0-listener-10` shows the same message once.
- The gate counted `connected` events only. The harness had no `TrackSubscribed` handling, no
  `getRtcStats()` sampling and no disconnect handling, so a listener that never received media — or
  dropped mid-hold — was invisible.
- The P8.3.8 report stated "MP_40 40/40 … all workers cleaned". That remains true for **connection and
  teardown**; it is **not** evidence that 40 participants received audio.

### E4 — P8.3.7 generator CPU measurements were invalid

- Evidence: the P8.3.7 monitor reported `GEN_cpu` 661–1237% (avg ≈888%). At t+24 s it reported
  `GEN_cpu=1034%` and LiveKit 222% (12.6 cores) while the same sample's host-wide busy CPU was 29%
  (≈5.2 of 18 cores) — the generator alone cannot use more CPU than the whole host.
- The monitor script was not preserved, so the exact defect is unknown; the figure is void.
- *Addendum (2026-10-04, see E9):* the comparison above used `/proc/stat` busy, which under-reads exact
  task runtime by 25–50 % on this kernel, so "exceeded the whole host" is weaker than stated (2.4× against
  a reference that can read up to 2× low on light load). The conclusion stands because the monitor
  script was lost and the figure cannot be reproduced or checked.
- Consequence: **generator CPU per participant is unmeasured**. RSS figures (≈450 MiB per
  10-participant worker process; ≈31 MiB per participant summed) are usable only as an **upper bound**
  (summed VmRSS double-counts shared pages). P8.4 measures generator cost from scratch (design §16).

### E5 — the watchdog was ad-hoc, not committed

- The P8.3.7 watchdog was a bash script in a session scratch directory. Only its outputs survive; the
  script (and therefore its exact sustain semantics) does not.
- Thresholds it used (recorded from the P8.3.7 instructions): hottest-core `%sys+%soft` > 85%;
  MemAvailable < 8 GiB; swap > 0; UDP RcvbufErrors/InErrors delta > 50; softnet drop delta > 50;
  conntrack > 209,000; LiveKit health ≠ 200; any container restart.
- In repo code, thresholds exist only as display strings (`scenarios/catalog.ts`); the supervisor aborts
  only on connect/publish failure or a worker crash. There is no SIGTERM handling, and a worker waits only
  for an IPC `shutdown`, so killing the supervisor could leave media sessions connected.

### E6 — multi-host coordination did not exist

- The supervisor forks local workers over Node IPC (`mp/supervisor.ts`). Run IDs are per supervisor;
  room and identity names derive from the scenario ID only (`core/identity.ts:27-34`); every supervisor
  deletes the room in `finish()`. Two hosts running the same scenario would evict each other's
  identities and delete each other's room.

### E7 — plan F3: nginx connection multiplicity (correction to `p8-load-capacity-plan.md` §0)

- The plan assumed 2 nginx connections per signalling WebSocket (≈6–7k clients). The deployed chain is
  `client → 443 (stream, ssl_preread) → 127.0.0.1:8443 (http, TLS) → 127.0.0.1:7880`, i.e. **4 nginx
  connections per WebSocket**. With 18 workers × `worker_connections 768` the balanced ceiling is
  ≈3,450 clients, and lower under accept imbalance. See design §15.

### E8 — plan §11: audio bandwidth model understated

- The plan used ~40 kbps per listener stream. The publisher's audio is published as **`audio/red`**
  (12/12 load-test `mediaTrack published` audio lines in the Phase 0 cross-check), and the model omitted
  packet headers. With RED, modelled per-listener egress is ≈86–118 kbit/s (Opus 32–48 kbit/s + RED +
  RTP/SRTP/UDP/IPv4 headers at 50 packets/s), i.e. ≈0.86–1.18 Gbit/s at 10,000 listeners, more on the
  wire. That is above the plan's 700 Mbit/s TX stop, which the model reaches at roughly 5.9k–8.1k
  listeners. This is a model only; P8.4 measures bytes per listener at every rung (design §14, §16).

### E9 — `/proc/stat` host busy is tick-sampled and under-reads exact runtime (added 2026-10-04)

- Found by: the P8.4 pre-commit real validation (local publisher + 1 listener, real LiveKit). The new
  E4 sampler check fired on a real host: the local generator's processes used 513 CPU ticks in a window
  where `/proc/stat` showed 393 busy ticks for the whole host; over the 45 s run the processes (≈4,400
  ticks incl. LiveKit and the controller) also exceeded `/proc/stat` busy (3,748).
- Mechanism, measured on the SUT (kernel `CONFIG_HZ=1000`, `NO_HZ_FULL=y`, `VIRT_CPU_ACCOUNTING_GEN=y`):
  a periodic test process was compared over 10 s windows against `/proc/schedstat` `rq_cpu_time`
  (the scheduler's exact clock, idle excluded).

  | Workload | `/proc/stat` host busy | Exact host task runtime | Process `utime+stime` | Process exact runtime |
  |---|---|---|---|---|
  | 2 ms every 10 ms | 386 ticks | 772 ticks | 255 | 255 |
  | 0.5 ms every 10 ms | 260 ticks | 344 ticks | 69 | 70 |
  | 8 ms every 10 ms | 941 ticks | 1,255 ticks | 773 | 773 |

  Per-process times match the exact runtime; host busy is charged only to whoever runs at the timer
  tick, so short bursts that sleep before the next tick are never charged.
- Consequences: (1) P8.3 host-wide busy percentages are **lower bounds**. (2) E4's reasoning is weaker
  than written (addendum on E4). (3) P8.4's V-sampler E4 check now compares exact against exact:
  Σ per-process CPU ≤ Σ `/proc/schedstat` `rq_cpu_time` (+ skew allowance). (4) **Open decision:** the
  P8.4 host CPU rules (S-cpu-total, S-cpu-hot, G-cpu, G-cpu-hot) still read `/proc/stat` and may under-read
  light, bursty load; at high utilisation the bias shrinks but was still −25 % in the 8 ms/10 ms case.
  Whether to switch them to `/proc/schedstat` is recorded in the verdict table for approval.
- *Addendum (2026-10-05, decision D-12):* `/proc/schedstat` `rq_cpu_time` is exact only **cumulatively**:
  it is credited when a task is switched out (kernel `sched_info_switch` → `rq_sched_info_depart`) and,
  per the same kernel source, skips the idle task — so softirq work done while a CPU was idle is never
  credited (source-derived, not measured). Measured on the SUT over
  500 ms windows, a core pinned at 100 % read 154, 0, 0, 242, 141, 0, 172, 96, 0, 0, 0, 460 %, and E4
  against it false-fired in 3 of 12 windows under one busy loop. Consequence (3) above is therefore
  superseded, and consequence (4) is closed: E4 and the CPU rules use per-core **wall − idle − iowait**,
  where idle and iowait come from the NO_HZ idle clock (`get_cpu_idle_time_us`: exact and ktime-based;
  per kernel source, idle accounting stops on irq entry, so irq/softirq time counts as busy). On the
  same pinned core it read 100.0 % in every window; on the
  2 ms/10 ms burst it matched schedstat's mean (27.9 % vs 27.5 %) while the busy ticks read 16.5 %.

## What is unaffected

- P8.3.6 publisher-first sequencing, P8.3.7 global ramp pacing (as a burst fix) and P8.3.8 worker
  teardown/process accounting remain correct for what they claimed.
- The SUT was verified clean after every P8.3 run (0 rooms, 0 DB rows, 0 stray processes, 0 restarts).
